# CWE-606 Sagent 分析规则

本文件合并该 CWE 的攻击面、候选模型、传播/生命周期复核、误报排除和输出约束。重点：循环/递归终止条件、外部计数、上界、超时、限流和资源耗尽。

# 18 搜查拒绝服务（DoS）

本轮目标：**识别可用网络请求触发的服务崩溃或资源耗尽**。

## 搜查模式

1. **空指针解引用**：
   - 关键校验缺失，特定输入触发 NULL 指针访问

2. **除零**：
   - `len / count` 且 count 可控为 0

3. **无限循环**：
   - while 条件依赖可控输入，构造特定值不退出
   - 递归无深度限制

4. **资源耗尽**：
   - 未限制连接数（fd 泄露）
   - 未限制每请求内存（一次请求让服务分配 GB 级内存）
   - 未限制单次请求解析时间（压缩炸弹、正则回溯）

5. **崩溃路径**：
   - assert 在网络可达分支（生产 assert = 进程崩溃）
   - 未捕获异常导致进程终止

## 起点

本仓库不产出 `clues/`、`notes/` 等 vh 风格线索文件——下文引用的线索文件一律不存在，忽略它们，改用「Sagent 工具与证据规则」的 GhidraMCP/query_sink_paths/ELF 解析工具自行收集。

优先级从高到低：

1. **`notes/01-protocol.md`** — 所有网络入口 handler（DoS 的发起点）
2. **`notes/02-attack-surface.md`** — 每个 handler 消耗什么资源（内存、线程、fd）
3. **`clues/semgrep-findings.md`** — 规则 category 含 `dos` / `null_pointer` / `memory_exhaustion` 的命中
4. **`clues/dangerous-sinks.md`** — `network_recv` 章节（"recv 长度 → malloc 这个长度"是典型资源耗尽模式）
5. **自主探索**：
   - `binary/main/imports.txt` 搜 `malloc`、`fork`、`pthread_create`、`assert`、`abort`、`exit`、`_exit`
   - 在 `binary/main/decompile/*.c` 搜 `recv(fd, &len); malloc(len); recv(fd, buf, len);` 模式
   - 搜 `while (...)` 循环条件依赖网络输入的情况

## 步骤

1. 对每个 handler：
   - 能否不带认证触发？（影响 DoS 严重度）
   - 是否分配内存 / 创建连接 / 启动线程？
   - 资源限额在哪里？
2. 寻找 assert、abort 在处理网络数据分支的调用
3. 寻找无限/大量递归模式

## 判定规则

- ✅ 漏洞：可构造网络请求导致崩溃 / 大量资源消耗
- ❌ 无：有资源限额和异常保护
- ❓ 疑似

## 产出约束

有漏洞：`vulns/VULN-NNN-dos-<子类型>.md`

`漏洞类型` 字段：
- `denial_of_service`
- `null_pointer_deref`
- `infinite_loop`
- `memory_exhaustion`
- `fd_exhaustion`
- `crash_on_input`

无漏洞：`notes/18-dos.md`。


## 硬性前置要求（所有漏洞类型通用）

### 1. 网络可达性是必要条件

本系统**只收录能通过网络请求触发的漏洞**。对每个候选漏洞，必须从网络入口（`notes/01-protocol.md` 的 dispatch 表）出发，逐跳证明可达。

- 如果路径追不回网络入口（例如只在本地启动时调用一次，或只被某个单元测试调用）→ **不创建 vulns 文件**，在对应的 notes 里记"本地可达但非网络可达"
- 如果前置需要认证但认证本身无漏洞 → 仍算网络可达，但严重度降级，并在 `基本信息` 中明确"需认证"

### 2. 去重：同一漏洞不写两份报告

**"同一漏洞"判定标准**：**sink 调用点地址相同**（例如同一处 `popen` 或同一处 `strcpy`），哪怕从不同入口/不同上游函数到达。

- 第一次发现：创建 `vulns/VULN-NNN-*.md`
- 发现"另一条调用链也能到达同一 sink"：**不创建新文件**，而是在已有的 vulns 文件的 `## 调用链` 章节里**追加一条入口路径**
- 判定前**必须先 Grep 现有 `vulns/` 目录**，确认 sink 地址是否已被记录

**例外**：同一函数但不同 sink 点（例如同一函数里既有 `system` 又有 `fopen` 两处漏洞）算两个漏洞，各写一份。

### 3. 不破坏已有的 vulns 文件

更新已有漏洞文件时，**只追加**调用链和数据流信息，不修改原有章节的事实描述。

## 反作弊声明

- DoS 严重度取决于触发成本（一次请求即崩 vs 需要大量请求）
- 只有 Critical / High 级别的 DoS 才创建 vulns，轻度的仅记 notes

## Sagent 工具与证据规则

1. 先使用 ELF 分析组中的 binaryID 和依赖关系确定范围，再使用 GhidraMCP 查询程序信息、导入、函数、字符串、反编译、调用关系和交叉引用。
2. 对高价值 sink 或生命周期事件调用 `query_sink_paths`；工具返回的 `path_found` 只是参数定义或依赖链，不能单独证明完整漏洞。
3. 每个结论必须引用 binaryID、functionID、调用点/地址和 evidenceIDs。Agent 推断必须标记为语义判断，不能把函数名或调用关系当作事实。
4. 从网络、IPC、命令行、环境、配置或文件入口逐跳检查可达性；认证要求、跨库边界、间接调用、别名和反编译限制都要记录。
5. 复核同一 sink 调用点的去重情况，不能因为多条入口路径重复创建同一个 finding。

## Sagent 最终输出规则

最终 JSON 必须包含 `findings`、`unresolved`、`coverage`。`findings[].status` 只能是 `confirmed` 或 `rejected`：

- `confirmed`：类型语义、外部可达性、传播/生命周期关系和安全影响均有工具证据；
- `rejected`：有明确反证，例如常量、路径不可达、有效校验、互斥控制流或对象实例不同。

证据不足、工具不支持、查询失败、跨组件未覆盖或只能提出候选时，不得放入 findings，改写入 `unresolved`，保留原因和 evidenceIDs。不要生成或执行 PoC；PoC 由独立阶段接收 confirmed findings。
