# CWE-190 Sagent 分析规则

本文件合并该 CWE 的攻击面、候选模型、传播/生命周期复核、误报排除和输出约束。重点：整数位宽、符号、截断、算术溢出、分配大小、索引和长度校验。

# 10 搜查整数相关漏洞

本轮目标：**识别整数溢出、符号错误、截断导致的安全问题**。

## 搜查模式

1. **有符号/无符号混淆**：
   ```
   if ((int)len < 256) {           // signed 比较
       memcpy(dst, src, len);      // 但 memcpy 用 size_t（unsigned）
   }
   // len = 0x80000000 时，(int)len = 负数，<256 通过；memcpy 当 unsigned 用，读巨量数据
   ```

2. **整数溢出**：
   ```
   total = header_len + body_len;  // uint32
   buf = malloc(total);            // 若 total 溢出到很小
   memcpy(buf, header, header_len);
   memcpy(buf+header_len, body, body_len);  // 溢出
   ```

3. **截断**：
   ```
   uint64_t len = recv_len();
   uint32_t n = len;               // 高 32 位截断
   if (n < SOMETHING) ...          // 绕过校验
   ```

4. **下溢 (underflow)**：
   ```
   size_t remaining = total - consumed;  // consumed 可能 > total
   memcpy(dst, src, remaining);          // remaining 变成巨大值
   ```

5. **数组下标负数**：
   ```
   int idx = parse_from_network();  // 可为负
   arr[idx] = ...;                  // 越界写
   ```

## 起点

本仓库不产出 `clues/`、`notes/` 等 vh 风格线索文件——下文引用的线索文件一律不存在，忽略它们，改用「Sagent 工具与证据规则」的 GhidraMCP/query_sink_paths/ELF 解析工具自行收集。

优先级从高到低：

1. **`clues/dangerous-sinks.md`** — `network_recv` 章节（recv 的长度参数是最常见的"可控整数源头"）
2. **`clues/semgrep-findings.md`** — 规则 category 含 `buffer_overflow` 的命中（很多堆/栈溢出的根因其实是整数错误）
3. **`notes/02-attack-surface.md`** — 污染从网络到 size 参数的路径
4. **自主探索**：
   - 用 Grep 在 `binary/main/decompile/*.c` 搜 `malloc/calloc/memcpy/read/recv/fread` 的 size 参数，识别非字面量来源
   - 搜 `if (.* < .*)` / `if (.* > .*)` 里的 len/size 比较，判断类型是否混淆（signed/unsigned）
   - 搜数组下标 `[i]`、`[idx]`，判断下标来源是否可控且可为负

## 步骤

1. Grep `imports.txt` + 反编译代码，找所有 size 计算点
2. 对每个计算：
   - 操作数的类型（signed / unsigned / size_t）
   - 每个操作数的取值范围（是否可控？是否有校验？）
   - 运算是否可能溢出/下溢/截断
3. 追可达性

## 判定规则

- ✅ 漏洞：可构造特殊输入触发溢出/截断并绕过后续校验
- ❌ 无漏洞：类型统一且有足够范围校验
- ❓ 疑似：类型可疑但后续 sink 未分析

## 产出约束

有漏洞：`vulns/VULN-NNN-int-<子类型>-<函数名>.md`

`漏洞类型` 字段：
- `integer_overflow`
- `integer_underflow`
- `sign_confusion`
- `integer_truncation`
- `negative_array_index`

无漏洞/疑似：`notes/10-integer-issues.md`。


## 硬性前置要求（所有漏洞类型通用）

### 1. 网络可达性是必要条件

本系统**只收录能通过网络请求触发的漏洞**。对每个候选漏洞，必须从网络入口（`notes/01-protocol.md` 的 dispatch 表）出发，逐跳证明可达。

- 如果路径追不回网络入口（例如只在本地启动时调用一次，或只被某个单元测试调用）→ **不创建 vulns 文件**，在对应的 notes 里记"本地可达但非网络可达"
- 如果前置需要认证但认证本身无漏洞 → 仍算网络可达，但严重度降级，并在 `基本信息` 中明确"需认证"

### 2. 去重：同一漏洞不写两份报告

**"同一漏洞"判定标准**：**sink 调用点地址相同**（例如同一处 `popen` 或同一处 `strcpy`），哪怕从不同入口/不同上游函数到达。

- 第一次发现：创建 `vulns/VULN-NNN-*.md`
- 发现"另一条调用链也能到达同一 sink"：**不创建新文件**，而是在已有的 vulns 文件的 `## 调用链` 章节里**追加一条入口路径**
- 判定前**必须先 Grep 现有 `vulns/` 目录**，确认 sink 地址是否已被记录

**例外**：同一函数但不同 sink 点（例如同一函数里既有 `system` 又有 `fopen` 两处漏洞）算两个漏洞，各写一份。

### 3. 不破坏已有的 vulns 文件

更新已有漏洞文件时，**只追加**调用链和数据流信息，不修改原有章节的事实描述。

## 反作弊声明

- 必须明确写出操作数的类型（从反编译代码或汇编推断）
- 提出的"构造输入"必须说明：用什么具体值能触发
- 不要把所有算术运算都当可疑，要结合"结果用于什么 sink"判断危害

## Sagent 工具与证据规则

1. 先使用 ELF 分析组中的 binaryID 和依赖关系确定范围，再使用 GhidraMCP 查询程序信息、导入、函数、字符串、反编译、调用关系和交叉引用。
2. 对高价值 sink 或生命周期事件调用 `query_sink_paths`；工具返回的 `path_found` 只是参数定义或依赖链，不能单独证明完整漏洞。
3. 每个结论必须引用 binaryID、functionID、调用点/地址和 evidenceIDs。Agent 推断必须标记为语义判断，不能把函数名或调用关系当作事实。
4. 从网络、IPC、命令行、环境、配置或文件入口逐跳检查可达性；认证要求、跨库边界、间接调用、别名和反编译限制都要记录。
5. 复核同一 sink 调用点的去重情况，不能因为多条入口路径重复创建同一个 finding。

## Sagent 最终输出规则

最终 JSON 必须包含 `findings`、`unresolved`、`coverage`。`findings[].status` 只能是 `confirmed` 或 `rejected`：

- `confirmed`：类型语义、外部可达性、传播/生命周期关系和安全影响均有工具证据；
- `rejected`：有明确反证，例如常量、路径不可达、有效校验、互斥控制流或对象实例不同。

证据不足、工具不支持、查询失败、跨组件未覆盖或只能提出候选时，不得放入 findings，改写入 `unresolved`，保留原因和 evidenceIDs。不要生成或执行 PoC；PoC 由独立阶段接收 confirmed findings。
