# CWE-416 Sagent 分析规则

本文件合并该 CWE 的攻击面、候选模型、传播/生命周期复核、误报排除和输出约束。重点：free/delete 后的读写、解引用、虚调用、别名、重分配和线程生命周期。

# 16 搜查 Use-After-Free

本轮目标：**只识别 Use-After-Free，不把 Double Free 或未初始化内存并入本类**。

## 搜查模式

1. **Use-After-Free**：
   ```c
   free(p);
   ...
   strcpy(p, ...);    // UAF
   ```
   或 C++ 中：
   ```cpp
   delete obj;
   obj->method();     // UAF via vtable
   ```

2. **Double-Free**：
   ```c
   free(p);
   if (error) free(p);  // 某条错误路径上重复 free
   ```

3. **使用未初始化内存**：
   ```c
   char buf[256];       // 栈上未清零
   some_func(buf);      // some_func 内部可能读 buf 未写区
   send(fd, buf, 256);  // 发送出去，泄露栈残留
   ```

4. **释放后野指针**：
   - 全局/成员指针被 free 但未置 NULL，后续被访问

## 起点

本仓库不产出 `clues/`、`notes/` 等 vh 风格线索文件——下文引用的线索文件一律不存在，忽略它们，改用「Sagent 工具与证据规则」的 GhidraMCP/query_sink_paths/ELF 解析工具自行收集。

优先级从高到低：

1. **`clues/semgrep-findings.md`** — 规则 category 含 `uaf` / `double_free` / `memory` 的命中
2. **`notes/01-protocol.md`** — 网络入口（追可达性）
3. **`notes/02-attack-surface.md`** — handler 处理流程（看对象生命周期）
4. **自主探索**：
   - `binary/main/imports.txt` 和 `binary/deps/<so>/imports.txt` 搜 `free`、`operator delete`、`delete[]`
   - 在 `binary/main/decompile/*.c` 搜 `free(` 和 `delete ` 调用点
   - 看 C++ 类的析构、容器元素释放、错误路径的资源清理

## 步骤

1. 追踪所有 `free/delete` 调用点
2. 对每个释放的指针，追踪其后续使用
3. 检查类的析构函数 + 可能的多路径释放
4. 对发送到网络的 buffer，检查是否完全初始化

## 判定规则

- ✅ 漏洞：确认能构造出 UAF / double-free / 未初始化内存泄露的路径
- ❌ 无：生命周期管理正确
- ❓ 疑似：复杂的 C++ 对象生命周期未追清

## 产出约束

有漏洞：`vulns/VULN-NNN-mem-<子类型>-<函数名>.md`

`漏洞类型` 字段：
- `use_after_free`
- `double_free`
- `uninitialized_memory`
- `info_leak_via_uninit`

无漏洞/疑似：`notes/16-uaf.md`。


## 硬性前置要求（所有漏洞类型通用）

### 1. 网络可达性是必要条件

本系统**只收录能通过网络请求触发的漏洞**。对每个候选漏洞，必须从网络入口（`notes/01-protocol.md` 的 dispatch 表）出发，逐跳证明可达。

- 如果路径追不回网络入口（例如只在本地启动时调用一次，或只被某个单元测试调用）→ **不创建 vulns 文件**，在对应的 notes 里记"本地可达但非网络可达"
- 如果前置需要认证但认证本身无漏洞 → 仍算网络可达，但严重度降级，并在 `基本信息` 中明确"需认证"

### 2. 去重：同一漏洞不写两份报告

**"同一漏洞"判定标准**：**sink 调用点地址相同**（例如同一处 `popen` 或同一处 `strcpy`），哪怕从不同入口/不同上游函数到达。

- 第一次发现：创建 `vulns/VULN-NNN-*.md`
- 发现"另一条调用链也能到达同一 sink"：**不创建新文件**，而是在已有的 vulns 文件的 `## 调用链` 章节里**追加一条入口路径**
- 判定前**必须先 Grep 现有 `vulns/` 目录**，确认 sink 地址是否已被记录

**例外**：同一函数但不同 sink 点（例如同一函数里既有 `system` 又有 `fopen` 两处漏洞）算两个漏洞，各写一份。

### 3. 不破坏已有的 vulns 文件

更新已有漏洞文件时，**只追加**调用链和数据流信息，不修改原有章节的事实描述。

## 反作弊声明

- 反编译代码对 C++ 对象生命周期追踪不准，必要时看汇编
- 不要把所有 `free` 都报 — 必须找到后续使用的具体代码

## 本类边界
只报告释放后的读、写、解引用、虚调用或外部调用；同一实例重复释放属于 CWE-415。

## Sagent 工具与证据规则

1. 先使用 ELF 分析组中的 binaryID 和依赖关系确定范围，再使用 GhidraMCP 查询程序信息、导入、函数、字符串、反编译、调用关系和交叉引用。
2. 对高价值 sink 或生命周期事件调用 `query_sink_paths`；工具返回的 `path_found` 只是参数定义或依赖链，不能单独证明完整漏洞。
3. 每个结论必须引用 binaryID、functionID、调用点/地址和 evidenceIDs。Agent 推断必须标记为语义判断，不能把函数名或调用关系当作事实。
4. 从网络、IPC、命令行、环境、配置或文件入口逐跳检查可达性；认证要求、跨库边界、间接调用、别名和反编译限制都要记录。
5. 复核同一 sink 调用点的去重情况，不能因为多条入口路径重复创建同一个 finding。

## Sagent 最终输出规则

最终 JSON 必须包含 `findings`、`unresolved`、`coverage`。`findings[].status` 只能是 `confirmed` 或 `rejected`：

- `confirmed`：类型语义、外部可达性、传播/生命周期关系和安全影响均有工具证据；
- `rejected`：有明确反证，例如常量、路径不可达、有效校验、互斥控制流或对象实例不同。

证据不足、工具不支持、查询失败、跨组件未覆盖或只能提出候选时，不得放入 findings，改写入 `unresolved`，保留原因和 evidenceIDs。不要生成或执行 PoC；PoC 由独立阶段接收 confirmed findings。
