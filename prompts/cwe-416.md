# CWE-416 Sagent 分析规则

本文件合并该 CWE 的攻击面、候选模型、传播/生命周期复核、误报排除和输出约束。重点：free/close 后的读写、解引用、作参数传递、别名、重分配和线程生命周期。

# 16 搜查 Use-After-Free

本轮目标：**只识别 Use-After-Free（释放后使用），不把 Double Free 或未初始化内存并入本类**。

## 起点

本仓库不产出 `clues/`、`notes/`、`binary/`、`decompile/` 目录——vh 风格章节提到的线索文件一律不存在，忽略它们，改用「Sagent 工具与证据规则」的 GhidraMCP/query_sink_paths/ELF 解析工具自行收集。优先级从高到低：

1. **GhidraMCP 导入表/函数/反编译** — 找全部释放函数调用点：`free/fclose/pclose/closedir/munmap/delete`，以及释放之后对同一对象/同一内存的读写与传参（最精准）
2. **query_sink_paths** — 对释放**之后**的使用点查对象定义链（覆盖清单，保证不漏）
3. **网络入口与 dispatch 表** — 反编译 handler 与 opcode 分发表（用于追可达性）
4. **依赖库 ELF 解析**（bash：`nm -D`/`objdump -d`/`strings`）— 未加载库的释放与使用点（无 evidenceID，记 unresolved）
5. **自主探索**：函数指针（虚调用）使用、别名传递、多线程共享对象

## 搜查清单

对阶段 M 候选链摘要里的每一条链，以及工具枚举出的全部释放/使用点，**必须每个都给出明确结论**。候选链摘要中没有覆盖的释放点也要主动枚举，不得遗漏。**若整组没有任何堆释放导入（无 free/fclose/pclose 族），在 coverage 中把对应攻击面标 checked 并写明证据，不要强行报漏洞。**

## 步骤

1. **逐链判定**：按 per-chain-judgment.md 的协议，对候选链摘要中每一条链给出 confirmed / rejected / unresolved 的明确 verdict；机械来源（callgraph/import_table/plt_link）不是确认依据，每一跳仍需要反汇编调用点证据。
2. **sink 枚举兜底**：找全释放调用点与释放后的使用点（解引用、读写、作函数参数），对照候选链清单，未出现的单独判定。
3. **对象同一性与时间序**：使用点与释放点是否作用**同一对象**（同一变量/同一内存地址）；使用是否**程序序上晚于**释放且在**同一可达路径**上；释放后指针是否被重新赋值或置 NULL。
4. **使用形态**：使用是解引用/读写/传入 sink，还是仅指针值比较（仅比较不算利用）；函数指针（虚调用）被释放后调用按严重处理。
5. **对象来源**：被释放对象是堆分配还是栈/全局地址（栈对象超出作用域后再用是另一类错误，不报本 CWE，记 unresolved 注明）。
6. **追调用链到网络输入**：到达使用点的分支条件是否来自网络（决定是否网络可达）。
7. **驳斥清单（仅 confirmed 候选必须逐项通过）**：见 per-chain-judgment.md 的 R1 source 可控性 / R2 逐跳传播 / R3 清洗约束 / R4 构造与影响。每项最多一次补充查询。

## 判定规则

- ✅ **confirmed**：同一对象释放后在同一可达路径上被使用（读写/传参/调用）+ 分支条件网络可控（或无条件触发）+ 驳斥清单 R1-R4 全部通过，且符合 confirmation-policy.md 的确认标准（引用链级证据时 confirmationBasis=reference-chain）。
- ❌ **rejected**：使用在释放之前、释放后指针重新赋值/置 NULL、使用与释放分属互斥分支、或对象不同。反证写进 finding 的 limitations。
- ❓ **unresolved**：别名/函数指针无法确认同一性、跨组件生命周期未覆盖、整组无堆面无法排除时，写 unresolved，说明缺哪一类证据，保留 evidenceIDs。

## 产出约束

最终 JSON 是唯一产出（见「Sagent 最终输出规则」）。不创建 vulns/notes/clues 目录文件。

## 硬性前置要求（所有漏洞类型通用）

### 1. 网络可达性是必要条件

本系统**只收录能通过网络请求触发的漏洞**。对每个候选漏洞，必须从网络入口（recv/read 等输入源）出发，逐跳证明可达。

- 如果路径追不回网络入口（例如只在本地启动时调用一次）→ 记为 rejected，limitations 写"本地可达但非网络可达"
- 如果前置需要认证但认证本身无漏洞 → 仍算网络可达，但严重度降级，并在 limitations 中明确"需认证"

### 2. 去重：同一漏洞不写两份报告

**"同一漏洞"判定标准**：**sink 调用点地址相同**，哪怕从不同入口/不同上游函数到达。

- 发现"另一条调用链也能到达同一 sink"：**不创建新 finding**，而是在已有 finding 的 limitations/调用链描述里追加一条入口路径
- 判定前先核对已写出的 finding 列表，确认 sink 地址是否已被记录

**例外**：同一函数但不同 sink 点算两个漏洞，各写一份。

### 3. 反作弊声明

- 释放后仅指针值比较（不读写内存）**不是** UAF 漏洞
- 释放后指针重新赋值后再用**不是** UAF（是正常生命周期）
- 互斥分支上的"另一分支释放后再用"**不是** UAF
- 每个释放 sink **必须**在产出中被引用（有漏洞或在 unresolved 中说明未分析原因）
- "rejected" 结论必须给出具体理由（时间序/对象不同/重新赋值），不能只说"无漏洞"

## Sagent 工具与证据规则

1. 先使用 ELF 分析组中的 binaryID 和依赖关系确定范围，再使用 GhidraMCP 查询程序信息、导入、函数、字符串、反编译、调用关系和交叉引用。
2. 对高价值 sink 调用 `query_sink_paths`（被使用对象）；工具返回的 `path_found` 只是参数定义或依赖链，不能单独证明完整漏洞。
3. 每个结论必须引用 binaryID、functionID、调用点/地址和 evidenceIDs。Agent 推断必须标记为语义判断，不能把函数名或调用关系当作事实。
4. 从网络、IPC、命令行、环境、配置或文件入口逐跳检查可达性；认证要求、跨库边界、间接调用、别名和反编译限制都要记录。
5. 复核同一 sink 调用点的去重情况，不能因为多条入口路径重复创建同一个 finding。

## Sagent 最终输出规则

最终 JSON 必须包含 `findings`、`unresolved`、`coverage`。`findings[].status` 只能是 `confirmed` 或 `rejected`：

- `confirmed`：类型语义、外部可达性、传播/生命周期关系和安全影响均有工具证据；
- `rejected`：有明确反证，例如常量、路径不可达、有效校验、互斥控制流或对象实例不同。

证据不足、工具不支持、查询失败、跨组件未覆盖或只能提出候选时，不得放入 findings，改写入 `unresolved`，保留原因和 evidenceIDs。不要生成或执行 PoC；PoC 由独立阶段接收 confirmed findings。
