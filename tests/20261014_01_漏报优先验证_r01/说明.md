# 20261014_01 漏报优先验证 r01 说明

## 目的

对照用户本地 docker 中 vulnhuntr 的 PoC 报告（同一 demo server 二进制），验证两点：

1. 此前 12 个 run 全 0 confirmed 的根因是否在确认门禁（而非目标选择错误）；
2. `--confirmation recall` 漏报优先策略上线后，ground-truth 命令注入链能否产出 confirmed finding 并进入 PoC 阶段。

完整分析见 [`docs/17-确认门禁保守性分析与漏报优先策略.md`](../../docs/17-确认门禁保守性分析与漏报优先策略.md)。

```bash
    [--force] --output tests/20261014_01_漏报优先验证_r01/产物
```

## 根因与修复

- 根因 1（提示词规则层）：旧规则禁止函数内路径证据下输出 confirmed——已由 `--confirmation recall` 策略解决（docs/17 §4）。
- 根因 2（证据核验层）：`artifacts.py` finalize 要求 `item.binaryID == record.binaryID`，而 Ghidra 只加载 root binary、全部工具记录 binaryID=server，跨二进制 finding（归属 libauth）的真实证据被错杀，且 invalid_references 全局集合连坐同证据的其他 finding。修复：核验只查 evidenceID 存在、属于本分析组、工具未报错。回归测试：`test_cross_binary_evidence_attributed_to_root_binary_is_kept`（r01）。
- 附带修复：汇总行 `成功=len(reports)-failures`（原实现把失败任务也算成功）。
- 遗留（未修）：CWE-78 模板继承 vh 提示词，引用了 clues/notes/decompile 等 vh 产物目录，我们的运行时一个都不产出，模型会浪费探索时间找它们（第 1 轮失败 transcript 可见）。模板去 vh 化列入后续。

## 证据完整性

`scripts/check_evidence_integrity.py 产物` → run-656dc86af251 OK、run-3c27fd0aa510 OK（2/2）。

## 结论

- recall 策略生效：真实运行从"2 条链全被错杀"变为"链 A confirmed 且产出 PoC"，首次端到端产出 PoC 交付物。
- 链 B 的确认依赖调用点证据（模型两轮行为不同：有证据时确认、无证据时诚实降级），符合引用链级确认标准。
- `analysisStatus` 仍为 inconclusive（覆盖账本标准高于工具能力上限），但已不再阻止 confirmed finding 进入 PoC 阶段；PoC 阶段只看 confirmed findings。
