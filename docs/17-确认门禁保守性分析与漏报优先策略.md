# 确认门禁保守性分析与漏报优先策略

> 回答两个问题：①为什么所有实验轮次都是 0 confirmed；②为什么 vulnhuntr 能产出大量 PoC、我们在哪一道闸门因证据不足被拒。
> 配套改动：`--confirmation {recall,precision}` 确认标准开关（见 docs/17 对应代码提交）。

## 1. 现象

- 基线两轮（20261013_01）+ 并发一轮（20261013_02）共 **12 个有效 run，全部 `analysisStatus=inconclusive`、`confirmed=0`**。
- 但 docs/16 的 ground truth 明确：demo server（data/01_simple_demo/server）有**两条真实命令注入链**：
  - 链 A：网络 opcode 0x1000 分派 → `pthread_create(remoteExec)` → `recv` 写 cmd 缓冲 → `doSystem@0x401ba2` → `popen@0x401380`（同二进制、无过滤）。
  - 链 B：opcode 0x1002 → `authLogin` → `auth_verify`（libauth.so）→ `auth_log` → `system`（跨二进制）。
- 两条链在所有轮次中都只落在 `unresolved` 里当"候选"（run-89d083fc65cf unresolved[0][1]），从未进入 findings，PoC 阶段因此全部 `skipped_no_confirmed_findings`。

## 2. 我们在哪里因证据不足被拒（四道闸门，按拦截顺序）

1. **提示词规则层（主要拦截点）**。旧规则明文禁止："当前路径后端仅返回函数内定义依赖时，不能输出 confirmed finding"（prompts/common/report-schema.md）；CWE 模板要求 confirmed 必须"类型语义、外部可达性、传播/生命周期关系和安全影响**均有工具证据**"；source-sink-model 要求自定义 wrapper"由静态事实确认参数、返回值或调用点关系后才能进入 confirmed"。模型据此自我审查，把链 A 主动写成 candidate→unresolved——run-89d083fc65cf unresolved[0] 原文："因当前 paths 后端只返回函数内定义依赖链，按规则不能输出 confirmed finding，故列入 unresolved"。链 B 同理（unresolved[1]）。
2. **证据核验层（artifacts.finalize）**。finding 的 evidenceIDs 必须在本地工具记录中可核验。此前要求 `item.binaryID == record.binaryID`：Ghidra 会话只加载 root binary，所有工具记录的 binaryID 都是 server，而链 B 的 finding 正确归属 libauth → 6 条真实证据全判"证据引用无法核验"、finding 被移出；且 invalid_references 是全局集合，链 B 引用过的 `get_program_info`/`list_imports` 证据被连坐污染，导致 server 侧链 A 的 finding 同样被踢（run-656dc86af251 实测复现）。**已修复**：核验只看"evidenceID 是否存在、属于本分析组、工具未报错"，不再要求 binaryID 相等（分析组内跨二进制调用链天然需要跨 binary 引用）。libauth.so/liblog.so 未加载进 ghidra 会话（unresolved[2][3][9]）仍以 ledger 条目保留。
3. **覆盖账本层（coverage.finish_check）**。confirmed sink 需要每个 sinkParams 都有路径查询、攻击面要 checked+证据、存在 unresolved 项即 `canFinish=False`。账本不剥 finding，但把"覆盖充分"的门槛定义得高于工具能力上限（无跨函数污点查询工具），导致整轮永远 inconclusive。
4. **PoC 阶段入口**。poc-stage.md 只接受 confirmed finding（"输入只包含已经 confirmed 的 finding，其余状态一律不进入本阶段"），且项目规则禁止执行样本。于是 0 confirmed → 0 PoC，运行时验证这条证据通道完全不存在。

**根因链**：后端能力上限（paths 只给函数内 RDA、ghidra 只加载 root binary、禁止执行样本）→ 确认标准按"污点级证据"定义 → 模型被规则禁止输出 confirmed → 剩余的候选再被证据核验层拦住 → 全部 0 confirmed、0 PoC。

**模型推理误差是第二类漏报来源**：CWE-78 第 2 轮把链 A 的 finding 判为 rejected，理由是"path_recv 全局只有加载期值 0x403008，反汇编中无任何写引用……故命令串为常量"。recv/memcpy 等**调用方写入**（callee-write）本就不在反汇编里留下写指令，用"无写指令"推断"常量"是误推理——recall 策略已明文禁止这种推断。

## 3. 与 vulnhuntr 的对比：为什么 vh 能产出大量 PoC

vulnhuntr（ProtectAI，2024-10）在真实项目上报告了十余个带**可运行 PoC** 的 0-day（[官方 README](https://github.com/protectai/vulnhuntr)、[PyPI](https://pypi.org/project/vulnhuntr/)）。结构差异：

| 维度 | vulnhuntr | 本仓库（sagent） |
| --- | --- | --- |
| 输入域 | 源码仓库（Python/JS/PHP），代码文本即证据 | 二进制，证据只能是工具调用记录 |
| 证据形态 | 文件/函数/导入上下文，永远"可核验" | evidenceID 必须能对上本地 raw 记录（反幻觉门禁） |
| 跨函数/跨组件 | 自适应上下文把相关函数整体拉进窗口 | paths 只给函数内 RDA；ghidra 只加载 root binary |
| 确认机制 | LLM 提案 + **PoC 运行作为验证**（CREATE_POC → RUN_POC → STATIC_VALIDATION，最多 2 轮修正） | 静态证据门禁；禁止执行样本，没有运行时验证通道 |
| PoC 的角色 | **证据生成器**（跑不通就修正再跑） | **交付物**（只有 confirmed 才配产出） |
| 覆盖账本 | 无 | 有：unresolved/攻击面/逐参数路径查询会拦 complete |

结论：vh 的 PoC 多，不是模型更聪明，而是**证据闭环不同**——它用运行时结果当证据（跑通即确认），我们用静态工具记录当证据（还要过可核验门禁）。我们既没有它的源码输入，又自废了执行验证，还把确认标准定在后端能力够不到的高度，三重叠加必然 0 confirmed。

### 3.1 本地 vh 实测对照（docker task 5，同一 server 二进制）

用户本地 docker（vulnhunter:v1.2，127.0.0.1:18080）task 5 对 `data/01_simple_demo/server` 的 report：server 8 个 vulns、client 0 个——与我们的分析目标一致（我们每轮 manifest 根都是 server）。vh 也没有动态执行（"poc 脚本未在目标上执行"），其 PoC 是**静态生成器**。8 个 vulns 与我们的覆盖对照：

| vh 漏洞 | 位置 | 与我们轮次的关系 |
| --- | --- | --- |
| VULN-001 未认证 RCE（critical） | opcode 0x1000→remoteExec→doSystem→popen@0x401be7 | = 我们的链 A；recall 修复后已 confirmed（run-656dc86af251） |
| VULN-002 auth_log 命令注入（critical，token 比较前执行） | opcode 0x1002→authLogin→auth_verify→auth_log→system@0x1014a3 | = 我们的链 B；recall 修复后已 confirmed（同上） |
| VULN-003 未授权文件上传 | fopen@0x401908 | 攻击面/候选出现过，未进入 finding（CWE-78 范围外） |
| VULN-004 日志注入（low） | — | 未跟踪 |
| VULN-005 硬编码 token SGC2023_SECRET@0x104038 | — | 未跟踪 |
| VULN-006 liblog strcpy 栈溢出（critical） | entry[128]←message≤512 | CWE-121，不在本轮 CWE 集内 |
| VULN-007 threadArgs 单槽竞态 | — | 未跟踪 |
| VULN-008 线程/fd 耗尽 DoS | — | 未跟踪 |

对照结论：①我们与 vh 分析的是同一 server，差距不在目标而在门禁（链 A/B 的引用链证据我们早就在 unresolved 里写出，但被核验层错杀）；②vh 的 clues/notes/decompile 产物目录正是我们 CWE-78 模板继承自 vh 提示词引用的文件，我们的运行时一个都不产出，模型会浪费探索时间找它们（run 失败 transcript 可见）——这是模板继承遗留，需在模板里去 vh 化；③vh 报告端口写 8002（0x1f42），我们模型写 7986 属于模型算术错误，与门禁无关。

## 4. 漏报优先（recall-first）策略

按"前期主要降漏报、后期再降误报"的节奏，确认标准分两档（`--confirmation`）：

- **recall（当前阶段默认）**：confirmed 允许两种依据。`taint-path`（污点级，原标准）；`reference-chain`（引用链级）：source/sink 在导入表有证据 + 逐跳调用点有反汇编/交叉引用证据 + sink 参数有函数内 path_found + 攻击面有证据，limitations 必须写明"跨函数污点未经污点级验证"。新增规则：**调用方写入即外部来源**（recv/memcpy 的缓冲写不得判为常量）。
- **precision（后期降误报）**：只接受 taint-path；引用链级确认由**运行时硬门禁**降级为 unresolved（不依赖模型自觉）。

实现（本次提交）：

- `prompts/common/confirmation-policy.md`：两档策略文本；作为系统提示词最后一节按模式注入。
- `prompts/common/report-schema.md`：finding 增加可选 `confirmationBasis` 字段；确认标准改为按策略条件化。
- `src/agent/agent_report.py`：`confirmationBasis` 校验（taint-path | reference-chain）；`apply_confirmation_policy(report, mode)` 执行 precision 降级硬门禁。
- `src/agent/cli.py`：`--confirmation {recall,precision}`（默认 recall）；报告落 `confirmationMode`；任务级断点 equivalence 含 confirmation。
- 测试：test_workflow.py +3（22 全绿）、test_poc_cli.py +3（15 全绿）。

降误报阶段的钩子（后续启用）：`--confirmation precision` + docs/16 FP 台账（precision 轮次记录的 FP 用于收紧 prompt），无需再改门禁代码。

## 5. 验证

- 真实运行：demo server CWE-78、`--confirmation recall`，验证链 A/B 能否 confirmed 并进入 PoC 阶段（tests/20261014_01_漏报优先验证_r01，结果见该目录说明.md）。
- run-656dc86af251（recall 首次成功轮）：模型输出了 2 条 confirmed reference-chain finding（链 A 11 evidenceIDs、链 B 6 evidenceIDs），但被 binaryID 强相等核验错杀。修复后对同轮 raw 事后 finalize：2 条 confirmed 保留、unresolved 13→5、证据完整性检查通过。
- 诚实边界：CWE-415/416/190/134/606 在 demo 里确实没有对应缺陷，0 confirmed 对它们是正确的；真正的漏报只有 CWE-78 两条链。recall 策略把"能确认的"从"污点级全链"放宽到"引用链级"，代价是 limitations 里必须如实标注证据等级，为后期降 FP 留出审计口。

## 6. PoC 产出差异与两阶段搜索策略（第二轮追问）

用户追问（m03632）：simple_demo 上我们只能产出 3 个 PoC 吗？差异原因是什么？思路定调：**前期静态分析尽量扩大搜索范围，后期的 agent 判断再来降 FP**。

### 6.1 我们的 PoC 产出现状

`tests/**/poc/*.py` 共 4 份 PoC 文件，但全部是同一个洞——doSystem 命令注入（链 A）：run-d4832cfc3a71、历史轮次 run-4a9b6b216ae1、run-5e3cec028963、run-3c27fd0aa510。**唯一 PoC = 1 个洞**；vh 在 server 上产出 7 份 PoC（8 个 vulns）。用户数到的"3 个"是多轮重跑里链 A 的重复拷贝。

### 6.2 差异原因（四层，由外到内）

1. **CWE 插件覆盖差（结构性，最大头）**：vh 全类别扫描；我们 6 个 CWE 插件、每 run 一个 CWE。vh 7 个 PoC 只有 2 个属于 CWE-78（VULN-001/002 = 链 A/B）；VULN-003 文件上传（CWE-434）、VULN-005 硬编码 token（CWE-798）、VULN-006 strcpy 栈溢出（CWE-121）、VULN-007 竞态（CWE-362）、VULN-008 DoS（CWE-400）均无对应插件 → CWE-78 单跑的结构性检出上限就是 2。
2. **搜索范围收窄（本轮已修）**：CWE 模板的 sink 表是封闭集（CWE-78 run 只枚举命令注入 sink）；「起点」一节还引用不存在的 vh 线索文件（clues/dangerous-sinks.md 等）误导模型。修复：attack-surface.md 两阶段化 + 6 个模板去 vh 化。
3. **依赖库不在工具可查范围（链 B 不稳定的根因）**：Ghidra 会话只加载 root，libauth/liblog 的 sink 只能靠模型 nm/objdump（无 evidenceID）→ 链 B 一轮 confirmed、一轮 unresolved。本轮把 lib 侧枚举规范进 unresolved，稳定确认需 Ghidra 加载依赖库——任务 D 已交付多会话 Ghidra（见 部署与使用手册 §5.7），20261014_05 轮已验证链 B 稳定 confirmed。
4. **PoC 同洞重复**：重跑/断点把链 A 重复产出，非新发现。

### 6.3 两阶段搜索策略落地

- **第一阶段（静态搜索，宁滥勿缺）**：prompts/common/attack-surface.md 重写——root 用 GhidraMCP、依赖库用 nm -D/objdump -d/strings 枚举全组全类危险 sink（命令执行/文件/字符串内存/凭据），候选全部进 functionModels 或 unresolved，不允许以"与本 CWE 无关"为由跳过。
- **第二阶段（agent 判断，降误报）**：按 CWE 判定规则 + confirmation-policy 逐项确认/拒绝；lib 侧无 evidenceID 的候选只进 unresolved。
- **模板去 vh 化**：6 个 CWE 模板「起点」节加统一声明，线索文件引用改为 Sagent 工具指引。

### 6.4 覆盖 vh 剩余 5 个洞的后续选项

- 新 CWE 插件：CWE-121（liblog strcpy）、CWE-798（硬编码 token）、CWE-434（fopen 上传）、CWE-362/400（竞态/DoS）——模板+测试按现有插件范式扩展。
- Ghidra 加载依赖库：lib 侧查询可产 evidenceID，链 B 与 CWE-121 的 lib 证据不再依赖模型裸 objdump。
