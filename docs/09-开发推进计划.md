# Sagent 开发推进计划

状态：执行计划 v0。本文是当前 Agent、GhidraMCP、静态路径查询和证据工作流的实现计划。后续实现按阶段推进，阶段完成后进行对应验证；每个阶段使用独立、可回滚的提交。

## 目标

把当前可以调用生产级 Agent 和 GhidraMCP 的原型，推进为一个证据驱动的二进制漏洞分析工作流：

```text
elf.py 分析组
  → 攻击面侦查
  → source/sink 候选发现
  → 自定义函数安全模型确认
  → sink 参数级路径查询
  → 覆盖账本检查
  → 证据整合和误报复核
  → finding
  → 静态 PoC
```

OpenCode 是主 Agent 底座，Claude Code 用于辅助验证；GhidraMCP 是反编译、函数和二进制导航入口。Agent 负责规划和语义判断，确定性工具负责枚举、路径查询、地址定位和覆盖记录。

## 明确边界

本轮不做：

- 把 Agent 自己的自然语言判断当作完整污点分析；
- 把全部函数反编译文本放进上下文或单个 JSON；
- 一开始实现跨架构、全别名、全路径的完整污点引擎；
- 引入 RAG 或 TaintSage state cache；
- 自动执行样本、连接真实设备或生成未经证据门禁的可执行 PoC；
- 修改外部参考仓库。

## 阶段一：分析组接入

### 实现

让 Agent 入口先调用 `elf.py` 的分析组构建能力：

```text
输入 ELF / 目录
  → build_analysis_groups()
  → 分析组摘要
  → GhidraMCP 和 Agent 查询范围
```

分析组摘要包含：

- `analysisGroupID`；
- `binaryID`、路径、哈希和架构；
- root binary；
- 本地依赖和待处理依赖；
- 组件关系；
- 当前工具限制。

### 验收

- 单 ELF 和目录输入都能生成稳定分析组；
- 单 ELF 的依赖只来自明确传入的 `--dependency-root`，不扫描父目录；
- Agent 只收到分析组内的组件；
- 每条 Ghidra 证据能够关联 `analysisGroupID` 和 `binaryID`；
- 现有 ELF 依赖实验继续通过。

## 阶段二：函数安全模型

### 类型

实现 `FunctionSecurityModel`，内部字段采用程序员习惯的混合命名：

```text
binaryID
functionID
functionName
functionAddress
roles
cweTypes
sourceParams
sinkParams
propagationMap
status
confidence
evidenceIDs
limitations
```

函数角色包括：

```text
source / sink / sanitizer / wrapper / parser / auth_boundary
```

状态包括：

```text
candidate / confirmed / rejected / unknown
```

Agent 可以提出 candidate；静态工具或人工证据才能将其提升为 confirmed。

### 验收

- 可以从 GhidraMCP 事实登记外部函数候选；
- 可以登记自定义 wrapper；
- 证据不足时保留 candidate 或 unknown；
- 模型不保存完整反编译文本，只保存摘要和证据引用；
- 模型可以 JSON 序列化并恢复。

## 阶段三：分析覆盖账本

### 类型

实现 `AnalysisCoverageLedger`，记录：

```text
analysisGroupID
binaryIDs
attackSurfaces
sourceModels
sinkModels
pathQueries
pathStats
unresolvedItems
budget
finishCheck
```

路径查询状态必须区分：

```text
path_found / no_path / unknown / unsupported / failed
```

### 结束门禁

只有满足以下条件才能结束分析：

1. 高优先级攻击面都有 checked、rejected 或 unknown；
2. confirmed sink 的敏感参数都已查询；
3. candidate sink 已确认、降级或写入 unresolved；
4. unknown、unsupported 和 failed 都有原因；
5. 每个 finding 都引用 evidence ID。

未满足时只能继续查询，或输出 `inconclusive`。

### 规模约束

默认不为每个函数、查询和路径创建单独文件。采用：

```text
state/coverage-ledger.json
state/function-index.json
state/findings.json
candidates.jsonl
queries.jsonl
evidence.jsonl
events/analysis.jsonl
raw/
```

全量函数只保留轻量索引；候选模型、查询结果和证据采用稀疏保留；完整反编译和工具原始结果按需读取或缓存。设置候选函数、sink 查询、路径深度、节点数和证据字节预算。

## 阶段四：阶段化 Prompt

通用规则和 CWE 规则分开：

```text
prompts/common/
  evidence-rules.md
  attack-surface.md
  source-sink-model.md
  coverage-rules.md
  report-schema.md

prompts/cwe-78/
  attack-surface.md
  candidate-models.md
  propagation-review.md
  false-positive-review.md
  poc.md
```

第一批实现 CWE-78，随后复用结构加入 CWE-134。CWE-190 和 CWE-606 需要数值范围、循环和约束状态，等路径接口稳定后加入。

Prompt 要求 Agent：

- 先建立攻击面地图；
- 识别候选 source/sink 和自定义 wrapper；
- 请求静态工具确认参数传播；
- 区分 no_path 与 unknown；
- 按 source、sink、传播边、可达性和 sanitizer 顺序复核；
- 在覆盖账本未完成时输出 inconclusive 或继续查询。

## 阶段五：静态路径后端评估

先使用同一组真实 ELF 小样本比较现成路径后端：

- Mango：sink 驱动的现成漏洞路径分析；
- CTADL：基于 Ghidra P-code 的跨过程污点分析；
- angr RDA/FunctionHandler：必要时实现受预算限制的参数路径适配器。

测试至少包括：

1. 外部输入经过两层 wrapper 到命令执行 sink；
2. sink 参数为常量；
3. 输入经过白名单或转义；
4. 间接调用或别名无法解析；
5. 输入进入非敏感参数。

评估内容：

- source/sink 参数定位；
- 每条传播边和地址；
- unknown/unsupported 表达；
- 误报和漏报；
- 分析时间和输出规模；
- 部署成本和版本稳定性。

只有路径后端返回可复核证据后，才接入 `query_sink_paths`。Agent 不直接依赖具体后端名称。

## 阶段六：真实数据实验

### 实验 A：仓库现有 ELF

使用 `data/01_simple_demo/` 验证：

- 分析组传递；
- GhidraMCP 程序和架构识别；
- 导入、字符串、函数和调用关系查询；
- 候选 source/sink 输出；
- 证据和覆盖账本生成。

### 实验 B：真实编译 ELF 正反例

在 `tests/` 的新实验轮次生成实际 ELF，验证：

- 输入到 wrapper 再到 sink；
- 常量到 sink；
- 过滤后到 sink；
- 间接调用；
- 非敏感参数。

原始实验数据不修改，实验目录保存编译命令、输入、观察结果和结构化输出。

### 实验 C：大型分析组

验证：

- 函数数量增大时是否只保留高价值候选；
- 单个 JSON 和 prompt 是否有大小上限；
- Agent 是否遵守覆盖账本结束条件；
- budget_exhausted 是否进入 inconclusive；
- 中断后是否能从紧凑状态恢复。
