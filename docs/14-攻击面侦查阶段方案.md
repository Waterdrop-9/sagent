# 攻击面侦查阶段方案（现状核实 + 补齐计划）

状态：设计稿 v0（2026-10-13）。回应问题：「当前似乎没有 vulnhunter 那样对每个 group 进行攻击面分析？我记得之前有计划先做攻击面分析再考虑后续的。」

## 1. 现状核实：有攻击面分析，但不是独立阶段

Sagent **有**攻击面分析，但形态与 vulnhunter（vh）不同：

| 维度 | Sagent 现状 | vulnhunter |
|---|---|---|
| 规则来源 | `prompts/common/attack-surface.md`：网络服务、IPC、命令行、环境变量、配置与设备节点、动态加载、认证与权限边界；危险 API 只算候选，需调用点/参数/可达性证据确认 | 独立阶段 `02-attack-surface.md`：从每个网络入口向内追踪，产出被污染函数清单 |
| 上游输入 | Agent 现场从 import/strings/xrefs 收集 | 独立阶段 `01-protocol.md` 产出的协议与 dispatch 表 |
| 持久化产物 | 无独立文件；attackSurfaces 只进 `report.json` 的 coverage 节 | `notes/01-protocol.md`、`notes/02-attack-surface.md`（per-handler 污染传播图） |
| 门禁 | `coverage.py` 账本：攻击面必须 checked/rejected/unknown 且带证据，unknown 必须有 reason；`agent_report.py` 校验结构 | `02b-network-surface-gate.md`：程序化二选一（`FOOLISH_STOP_NO_NETWORK_SURFACE` / `FOOLISH_CONTINUE`），无网络攻击面直接终止 |
| 复用 | 每个 CWE 分析重复侦查一遍（`--cwe all` 时同一 group 侦查 6 次） | 一次产出，全部后续漏洞阶段复用 |
| 计划依据 | docs/09 流水线第一、二步即「攻击面侦查 → source/sink 候选发现」，阶段四 prompt 要求「先建立攻击面地图」 | — |

结论：早期计划（docs/09）确实把攻击面侦查放在流水线最前面，但当前实现把它**折叠进了每个 CWE 分析的 Agent 任务**里——没有独立阶段、没有持久化产物、没有跨 CWE 复用、没有「无攻击面即跳过」的门禁。这就是「看起来没有」的原因。

## 2. 补齐方案

### 2.1 新增独立阶段：攻击面侦查（阶段 0）

每个分析组**一次**、在任何 CWE 分析之前运行：

```text
elf.py 分析组
  → 攻击面侦查（新阶段 0，独立 Agent 请求，产物持久化）
  → 网络攻击面门禁（无攻击面 → 后续 CWE 阶段跳过）
  → source/sink 候选发现 → …（原有流水线不变）
```

产物落 `<run>/state/attack-surface.json`（schema 草案）：

```json
{
  "analysisGroupID": "group-…",
  "stage": "attack-surface",
  "listeners": [{"port": 8002, "transport": "tcp", "bindAddress": "0.0.0.0", "evidence": ["ev-…"]}],
  "protocols": [{"kind": "custom-binary", "layout": "opcode(2B, 0x1000 小端) + 载荷", "evidence": ["ev-…"]}],
  "dispatch": [{"trigger": "opcode 0x1000", "handler": "remoteExec", "address": "0x401cbc", "authRequired": "none|unknown|yes", "evidence": ["ev-…"]}],
  "entryFunctions": [{"functionID": "…/remoteExec", "role": "recv 后第一落点", "inputs": ["recv(sockfd, buf, 0x400)"], "evidence": ["ev-…"]}],
  "taintedFunctions": [{"functionID": "…/doSystem", "taintedParams": [0], "flowsTo": ["popen@0x401380"]}],
  "crossBinaryCalls": [{"caller": "…/server", "callee": "liblog.so:log_message", "mayCarryNetworkData": true, "evidence": ["ev-…"]}],
  "networkReachable": true,
  "unresolved": []
}
```

设计要点（继承 vh 02 与 02b 的思想，套用 Sagent 契约）：

- **证据约束**：schema 里每项都带 evidence 引用，侦查阶段自己走 evidence_proxy + 证据门禁；危险 API 仍是候选，必须调用点/参数证据才进 dispatch/taintedFunctions（沿用 `attack-surface.md` 现有规则）。
- **dispatch 表完整性反作弊**（借鉴 vh 01）：opcode/路径必须精确到 `0x` 十六进制、覆盖 switch 全部分支；`authRequired` 未确认写 `unknown`，不许默认 `none`。
- **网络攻击面门禁**（vh 02b 的 Sagent 版）：同时满足「无网络 import 或全部证明为死代码 + dispatch 表为空 + 被污染函数列表为空 + 无 unresolved」才判 `networkReachable: false`；任何不确定都判 true。`false` 时后续 CWE 阶段的 report 记 `skipped_no_attack_surface`（新状态，区别于 `skipped_no_confirmed_findings`）。
- **跨 CWE 复用**：后续每个 CWE 分析把 attack-surface.json 的摘要（dispatch 表 + 入口函数，≤ 8KiB 预算）注入 prompt，Agent 不再从零侦查；账本中 attackSurfaces 的检查条款保留不变（产物预填 + 分析内复核双保险）。
- **运行方式**：`--attack-surface` 显式开关（或随 `--poc` 式 `[stage]` 配置）；`--cwe all` 时阶段 0 只跑一次。

### 2.2 与 TaintSage 接入的衔接

docs/13 的 P0（source 识别增强）需要「网络入口 → handler → recv 点」作为 source 端候选入口——攻击面产物的 `dispatch` + `entryFunctions` 正是这个上游。因此本方案是 docs/13 的前置依赖，建议实施顺序：本方案 → docs/13 P0 → docs/13 P1。

### 2.3 分阶段落地

| 步骤 | 内容 | 实验/验收 |
|---|---|---|
| A1 | 新增 `src/agent/attack_surface.py`（schema 校验 + 序列化，运行时无关）+ cli 阶段编排 + 新 report 状态 | r01 契约测试 + r02 fake 端到端（fake opencode 返回攻击面 JSON） |
| A2 | 网络攻击面门禁 + `skipped_no_attack_surface` 分支 | r02：无攻击面 fixture → 后续 CWE 全部跳过；有攻击面 fixture → 正常跑 |
| A3 | 攻击面摘要注入后续 CWE prompt（≤8KiB） | r02：第二次分析 prompt 含 dispatch 摘要 |
| A4 | 真实 sample：data/01_simple_demo 跑阶段 0（真实 OpenCode 一次），产物核验后归档 | 说明.md 记录观察 |

## 3. 明确不做

- 不复制 vh 的 `notes/` 文档树与 token 门禁（Sagent 用结构化 JSON + 覆盖账本）；
- 攻击面产物不替代 CWE 分析内的 attackSurfaces 账本条款；
- 不把「无攻击面」当作「无漏洞」结论——只是跳过昂贵阶段，report 必须写明跳过原因。
