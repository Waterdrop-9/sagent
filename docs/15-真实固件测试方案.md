# 真实固件测试方案

状态：设计稿 v0（2026-10-13）。目标：让 Sagent 在真实固件镜像上端到端跑通（解包 → 分析组 → 攻击面 → CWE 分析 → 证据门禁 → PoC 阶段），并在有公开 CVE 的固件版本上建立对照评测基线。依赖 docs/14（攻击面阶段）与 docs/13（TaintSage 接入）。

## 1. 现状与前提

- 当前 `data/` 只有 `01_simple_demo`（单 ELF + 2 个本地库），无固件样本；「固件解包（binwalk 适配器）、压缩包输入」在 PROGRESS.md 暂缓项。
- 约束：沙箱不执行样本、不连接真实设备（GUIDELINE）；PoC 阶段只产出静态审计材料与验证脚本（executed=false），动态验证（FirmAE/FIRMEE 重托管）仅作未来工作——TAINTSAGE 论文自身也把符号执行/动态验证列为未来方向。

## 2. 样本选型

| 来源 | 样本 | 用途 | 授权 |
|---|---|---|---|
| KARONTE 数据集（公开） | 49 个镜像（Tenda 7 / D-Link 9 / TP-Link 16 / NetGear 17） | 与论文 RQ4 同源，可对照口径（alerts / 人工 TP / precision） | 公开学术数据集 |
| 厂商官网/镜像站 | 3-5 个有公开 CVE 的具体版本（候选：Tenda AC15/AC18、D-Link DIR-859、NetGear R6400 系列） | CVE 对照评测（近似 recall） | 公开下载，记录来源+版本+哈希 |

样本落盘位置遵循 EXPERIMENT.md：实验目录内 `data/`（不入库）；不修改 `data/01_simple_demo`。每个镜像记录来源 URL、版本、SHA256 到实验说明。

## 3. 技术路径（6 步）

1. **解包适配器**（新能力，补暂缓项）：`binwalk -e` 解 squashfs/cpio → rootfs 识别（找 `/bin`、`/usr/sbin`、`/etc`、web 目录）；新增 `--firmware <镜像>` 入口（或 `src/agent/firmware.py`，复用 `analysis_context.py` 的组构建）；解包元数据（镜像哈希、rootfs 路径、提取出的 ELF 清单）记入 run 目录，必要时 evidence 化。
2. **Web 服务组件发现**（KARONTE 式）：从 rootfs 的 `www/`、`htdocs/`、`lua/` 脚本与前端文件，关联后端服务二进制（httpd/自研服务）；产出的「服务组件清单」作为 docs/14 攻击面阶段在固件上的输入（dispatch 表、入口函数）。
3. **分析组构建**：root binary + rootfs 共享库目录为 dependency-root；预期多二进制 unresolved「本地依赖及跨组件路径尚未覆盖」在 docs/13 P1（状态抽象）落地前持续存在，评测时如实记录。
4. **GhidraMCP 跨架构验证**：在 ARM/MIPS 样本上验证 headless 反编译、P-code、xrefs、字符串（Ghidra 原生多架构，需确认我们的 wrapper 无 x86 假设）；不支持的架构/文件格式要产生明确的 failed 记录而非静默。
5. **angr RDA 路径后端跨架构**：ARM/MIPS 的 CFGFast + RDA 在预算下验证；不支持的指令/重定位落到 `unsupported` 状态（账本已有该状态与 reason 条款）。
6. **CWE 分析与 PoC 不变**：confirmed 门禁、覆盖账本、PoC 静态审计材料（验证脚本面向模拟环境、人工执行）全部沿用现有契约。

## 4. 评测设计（CVE 对照）

- **选样**：3-5 个「NVD 有公开 CVE 且 CVE 命中本组支持类型（CWE-78/134/190/606）」的固件版本。
- **指标**（论文口径 + Sagent 口径）：
  - alerts（findings 总数）、confirmed 数、人工复核 TP 数、precision；
  - 已知 CVE 命中数 / 漏报数（近似 recall，CVE 只覆盖已知部分）；
  - unresolved 率（多二进制/跨架构的影响量化）、单镜像端到端耗时、字节预算触顶率。
- **目标**：不是复现论文 82.83%，而是得到 Sagent 自己的基线，并逐项归因差距（解包质量 / 组件发现 / 跨架构路径后端 / 状态抽象缺失）。
- **流程**：评测运行记录入实验目录 `产物/`；人工复核表（findingID ↔ CVE ↔ 判定）落 `说明.md`。

## 5. 分阶段实验目录（计划）

| 实验 | 内容 | 通过标准 |
|---|---|---|
| `tests/20261013_01_固件解包_r01/` | binwalk 适配器 + rootfs 识别 + 服务组件发现（2-3 个镜像，无 LLM） | 解包元数据完整、ELF 清单可复现、跨架构 ELF 识别正确 |
| `tests/20261014_01_固件跨架构_r01/` | ARM/MIPS 样本上 GhidraMCP + angr 路径后端验证（无 LLM） | 反编译/xrefs 正常；paths 查询有 path_found/unsupported 且 reason 完整 |
| `tests/20261015_01_固件CVE对照_r01/` | 3-5 个 CVE 固件全流程（含攻击面阶段与 PoC 阶段）+ 评测报告 | 全流程跑通、评测数字与归因记录完整 |

依赖顺序建议：docs/14（攻击面阶段）→ `固件解包` → docs/13 P1（状态抽象）→ `固件CVE对照`。

## 6. 风险与约束

| 风险 | 表现 | 缓解 |
|---|---|---|
| 大镜像耗时/空间 | Ghidra 分析大 rootfs 慢、产物超字节上限 | 先只分析服务组件二进制；MAX_* 上限按实测触顶率调整并记录 |
| angr 对 MIPS/ARM 的缺口 | 某些重定位/指令不支持 | `unsupported` 状态如实入账本（不算失败）；必要时按 docs/07 §9 引入第二后端交叉验证 |
| 无 ground truth 的误判 | TP 判定主观 | 复核表固定判定标准（触发点可被用户可控数据到达，沿用论文表注口径），仲裁留痕 |
| 样本供应链 | 镜像来源不明确/带毒 | 只取公开来源、记录 SHA256、不在沙箱执行 |
| 授权与合规 | 测试公开 CVE 样本的边界 | 仅静态分析；验证脚本标注「仅供授权环境」，不自动执行 |
