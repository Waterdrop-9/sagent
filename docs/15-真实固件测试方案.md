# 真实固件测试方案

状态：设计稿 v1（2026-10-13）。目标：让 Sagent 在真实固件上端到端跑通（解包 → 分析组 → 攻击面 → CWE 分析 → 证据门禁 → PoC 阶段），并在有公开 CVE 的固件版本上建立对照评测基线。依赖 docs/14（攻击面阶段）与 docs/13（TaintSage 接入）。

v1 相对 v0 的调整（用户要求，2026-10-13）：样本确定为 `data/02_two_firmwares/` 下的两个固件（用户提供，均为**已解包的 Tenda rootfs 树**，无需 binwalk）。

## 1. 现状与前提

- 样本已就位：`data/02_two_firmwares/` 两个 zip（见 §2），均为 Tenda 路由器 rootfs 目录树（含 `bin/httpd` 主 Web 服务与 `lib/` 共享库），不是原始固件镜像，因此**本轮不需要 binwalk 解包适配器**（binwalk 适配器退回暂缓项，用于未来原始镜像输入）。
- 约束：沙箱不执行样本、不连接真实设备（GUIDELINE）；PoC 阶段只产出静态审计材料与验证脚本（executed=false），动态验证（FirmAE/FIRMEE 重托管）仅作未来工作——TAINTSAGE 论文自身也把符号执行/动态验证列为未来方向。

## 2. 样本（data/02_two_firmwares/）

| 样本 zip | 内容 | 关键组件 | 已知 CVE 线索（评测时核对版本对应） |
|---|---|---|---|
| `AC18_V15.03.05.19_6318_CN_vulnhunter.zip`（41.8MB，841 文件） | Tenda AC18 rootfs（ARM，uClibc） | `bin/httpd`（989,824B，主 Web 服务）、`bin/dhttpd`（212,948B）、`lib/libCfm.so`、`lib/libcommon.so`、`lib/libcloud.so`、`webroot_ro/*.asp` | AC15/AC18 系列有公开命令注入 CVE（如 formSetDeviceName、goform 处理类），逐一核对 |
| `FH1203_V2.0.1.6_CN_SVN1134_vulnhunter.zip`（28.8MB，241 文件） | Tenda FH1203 rootfs（MIPS，uClibc） | 同结构（`bin/httpd`、`bin/cfmd`、`lib/`、`webroot_ro/`） | FH1203 有公开命令注入 CVE（如 formWriteFacMac 类），逐一核对 |

- 命名含 `vulnhunter` 后缀，应为 vulnhunter 项目测试语料的 rootfs 抽取版本（`*_CN` 国行固件）。
- 样本落盘遵循 EXPERIMENT.md：数据留在 `data/02_two_firmwares/`（zip 原样保留）；解压产物放实验目录内 `data/`（不入库）；不修改 `data/01_simple_demo`。每个 zip 记录 SHA256 到实验说明。

## 3. 技术路径（6 步）

1. **解压与架构确认**：`unzip` 解到实验目录 `data/`；用 `file` 确认 `bin/httpd` 等 ELF 架构（预期 AC18=ARM、FH1203=MIPS，均 uClibc）；解包元数据（zip 哈希、rootfs 清单、ELF 架构清单）记入实验说明。
2. **Web 服务组件发现**（KARONTE 式）：从 `webroot_ro/*.asp`、前端文件与 `bin/` 服务二进制关联后端（httpd/dhttpd/cfmd）；产出的「服务组件清单」作为 docs/14 攻击面阶段在固件上的输入（dispatch 表、入口函数）。
3. **分析组构建**：root binary=对应 `bin/httpd`（或目标服务二进制）+ rootfs `lib/` 目录为 dependency-root；预期多二进制 unresolved「本地依赖及跨组件路径尚未覆盖」持续存在（docs/13 v1 明确状态抽象本轮不做），评测时如实记录。
4. **GhidraMCP 跨架构验证**：在 ARM（AC18）与 MIPS（FH1203）样本上验证 headless 反编译、P-code、xrefs、字符串（Ghidra 原生多架构，需确认我们的 wrapper 无 x86 假设）；不支持的架构/文件格式要产生明确的 failed 记录而非静默。
5. **angr RDA 路径后端跨架构**：ARM/MIPS 的 CFGFast + RDA 在预算下验证；不支持的指令/重定位落到 `unsupported` 状态（账本已有该状态与 reason 条款）。
6. **CWE 分析与 PoC 不变**：confirmed 门禁、覆盖账本、PoC 静态审计材料（验证脚本面向模拟环境、人工执行）全部沿用现有契约。

## 4. 评测设计（CVE 对照）

- **选样**：`data/02_two_firmwares` 两个版本，先核对 NVD 中与这两个版本号对应的公开 CVE（命令注入/格式化串/整数溢出优先，即 CWE-78/134/190/606 范围）。
- **指标**（论文口径 + Sagent 口径）：
  - alerts（findings 总数）、confirmed 数、人工复核 TP 数、precision；
  - 已知 CVE 命中数 / 漏报数（近似 recall，CVE 只覆盖已知部分）；
  - unresolved 率（多二进制/跨架构的影响量化）、单镜像端到端耗时、字节预算触顶率、token 开销（配合任务②的日志系统）。
- **目标**：不是复现论文 82.83%，而是得到 Sagent 在两个真实 Tenda 固件上的基线，并逐项归因差距（组件发现 / 跨架构路径后端 / 状态抽象缺失）。
- **流程**：评测运行记录入实验目录 `产物/`；人工复核表（findingID ↔ CVE ↔ 判定）落 `说明.md`。

## 6. 风险与约束

| 风险 | 表现 | 缓解 |
|---|---|---|
| 大镜像耗时/空间 | Ghidra 分析大 rootfs 慢、产物超字节上限 | 先只分析服务组件二进制；MAX_* 上限按实测触顶率调整并记录 |
| angr 对 MIPS/ARM 的缺口 | 某些重定位/指令不支持 | `unsupported` 状态如实入账本（不算失败）；必要时按 docs/07 §9 引入第二后端交叉验证 |
| 无 ground truth 的误判 | TP 判定主观 | 复核表固定判定标准（触发点可被用户可控数据到达，沿用论文表注口径），仲裁留痕 |
| 样本供应链 | 镜像来源不明确/带毒 | 样本为用户提供；记录 SHA256、不在沙箱执行 |
| 授权与合规 | 测试公开 CVE 样本的边界 | 仅静态分析；验证脚本标注「仅供授权环境」，不自动执行 |
