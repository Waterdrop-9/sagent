# 候选链物化与逐链判定架构方案（前期降漏报、后期降误报）

状态：设计稿 v2（2026-10-13，含三轮评审修订：依赖库先验判定、M 加 LLM 语义分类、J 前置机械去重、驳斥式降 FP）。本方案落实用户确认的架构思路：「前期主要降漏报、后期再降误报——前面的静态分析分析链路和判据尽可能扩大覆盖面，后面的 agent 重新判断降低误报率；与 TaintSage 一致，前面的 RDC 生成覆盖面尽可能广，后面的 LLM 执行污点分析再降误报」。**本方案先评审、不写代码**；批准后按 §6 阶段逐段实施。

## 1. 架构思路（执行者分层，不是提示词分层）

| | 前期（静态分析机制） | 后期（agent 判断） |
|---|---|---|
| 执行者 | 确定性 Python 机制为主（elf.py + angr paths 后端）+ 一次有界 LLM 语义分类（§3.5 M2），失败可纯机械降级 | LLM（opencode 会话） |
| 职责 | 生成**候选链集合与候选判据**：全组 sink 枚举 → source 候选 → source→sink 依赖链物化 | 对每一条候选链做**污点级语义判定**：source 是否可控、逐跳是否传播、有无清洗 → confirmed / rejected / unresolved |
| 原则 | **覆盖面最大化，宁滥勿缺**，不做保守裁剪 | **降误报**，把机械阶段产生的 FP 逐链否掉 |
| 对应 TaintSage | DDC 提取 → RDC 物化（原始依赖链，机械生成） | LLM 污点分析（四类证据逐链判定） |
| Sagent 现状 | 不存在——候选链只存在于 LLM 对话里，**链集合 = 模型决定查询的那部分** | 与链生成混在同一个会话里：模型边枚举边自审，finalize 门禁在判定前删链 |

结论：现状把「广」与「收」都交给了同一个 LLM 会话，且「广」受模型探索行为约束。本方案把「广」下沉为确定性机制，LLM 只保留「收」。

## 2. 目标架构

```text
(每个 分析组 × CWE 任务，_run_pair 内)

阶段 M（候选物化：机械为主 + 一次有界 LLM 辅助）
  M1 机械枚举：elf.py 全组二进制解析
    → sink 枚举（root：import 表 + angr CFG 调用点；依赖库：elf.py 导入/动态符号）
    → source 候选枚举（外部输入函数调用点 + 入口函数 + rodata 候选）
    → 链物化：逐 sink 调 paths 后端 query_sink_paths（现有 DDC 等价物）
       + CFG callgraph 回溯 source→sink 函数路径 + PLT/导入表跨二进制连接
  M2 LLM 语义分类（一次有界调用，可降级跳过）：外部函数 (f,idx) 参数级角色识别、
      rodata 候选语义分类、自定义库/常见库判定（§3.5）
  M3 机械去重：等价链合并 / 保留更长链 / 共享下游合并（§3.6）
    → 落盘 state/risk-chains.json（全部候选，不裁剪）
    → 机械证据记录写入 raw/paths.jsonl（自签 evidenceID，LLM 可引用）

阶段 J（agent 逐链判定，原分析阶段）
  输入 = CWE 模板 + risk-chains.json 摘要（预算内）
  逐链污点判定 → findings/coverage/report.json（报告 schema 不变）
  confirmation 政策（recall/precision）仍在此生效 → 降误报
  finalize 证据门禁、coverage 账本、PoC 阶段全部不变
```

关键点：**报告与门禁契约不变**（findings、coverage、evidenceID 核验、账本、PoC 都不动），变的是 LLM 的输入形态（从"自己去枚举"变成"对给定候选链逐条判定"）和候选链的来源（机械全量 vs 模型探索）。

## 3. 阶段 M 设计（候选物化）

### 3.1 M1：新模块 `src/agent/risk_chains.py`（运行时无关、可单测）

输入：`AnalysisGroup`（elf.py 现有对象）+ CWE sink 家族表 + 目标二进制路径。
输出：`state/risk-chains.json` + 追加的 paths 证据记录。

- **sink 枚举**：每个 CWE 模板现有 sink 表抽成结构化常量（`sink_families: dict[str, set[str]]`，如 CWE-78 → {system, popen, execl…}）；root 用 angr CFG 找这些符号的调用点（path_query.py 已能做 `_resolve_function` + 调用点定位）；依赖库用 elf.py 的导入表/动态符号（本仓库纯 Python ELF 解析，无子进程、无模型依赖）。sink 全部枚举，**不做「先证可达再收」的裁剪**。
- **source 候选**：外部输入函数（recv/recvfrom/read/fgets/scanf…）的调用点 + 网络入口/opcode 分派落点函数 + rodata 高引用字符串候选；全部为候选，标注 kind 与机械证据。
- **链物化**：对每个 sink 调用点调 `AngrPathBackend.query`（现有 `PathQuery`，max_depth=8/max_nodes=5000 预算）拿参数定义链；用 CFG callgraph 从 source 候选函数向 sink 调用者做后向可达搜索（步数上限）生成函数路径；跨二进制用 PLT 地址→导入符号映射连起来。产物是**候选链**：`source → hops[] → sink`，每条带定义链证据引用与 limitations，**不在此阶段判定真伪**。
- **证据落账**：机械阶段自己把 paths 查询结果按 evidence_proxy 现有格式写入 `raw/paths.jsonl`（自签 ev- 前缀 ID），保证后续 finalize 门禁能核验 LLM 对机械证据的引用。

### 3.2 risk-chains.json schema（草案）

```json
{
  "stage": "risk-chains",
  "analysisGroupID": "group-…",
  "generatedBy": "mechanical",
  "sinkFamilies": {"CWE-78": ["system", "popen", "…"]},
  "sinks": [{"binaryID": "…", "functionID": "0x…", "name": "popen",
             "callSites": ["0x…"], "evidenceIDs": ["ev-…"]}],
  "sources": [{"binaryID": "…", "functionID": "0x…", "kind": "recv|entry|rodata",
               "evidenceIDs": ["ev-…"]}],
  "chains": [{
    "chainID": "ch-01",
    "source": {"functionID": "…", "kind": "recv"},
    "hops": [{"functionID": "…", "callsiteAddress": "0x…"}],
    "sink": {"functionID": "…", "argument": 0},
    "definitionChains": ["<paths 后端结果摘录>"],
    "evidenceIDs": ["ev-…"],
    "status": "candidate"
  }],
  "stats": {"sinks": 12, "chains": 34, "truncated": false}
}
```

### 3.3 预算与爆炸控制

- 每任务链注入 prompt 的摘要上限 **16 KiB**（全量 JSON 只在 state/ 落盘）；摘要超出时按 sink 严重度排序截断并标注 `truncated: true`。
- paths 后端预算沿用（每个 sink 一次查询、8 深度、5000 节点）；CFG 回溯步数上限（默认 6 跳）。
- 机械阶段失败/angr 缺失 → 降级为现状行为（LLM 自行枚举）并打 warning 日志，不阻塞任务。

### 3.4 待评审的决策点

1. **粒度**：v1 机械阶段按 (组 × CWE) 跑一次（简单、贴合 `--workers` 任务形态、无需跨 CWE 状态缓存）；跨 CWE 复用（同组 6 个 CWE 只物化一次）作为后续，与 docs/14 阶段 0 攻击面侦查合并做组级缓存。
2. **账本预填**：v1 不改 coverage 账本（LLM 仍逐链产出 functionModels）；是否把机械阶段的 sink/source 模型预填进账本（sink 覆盖从"模型记得写"变"机制保证"）留到 v1 验证后决定。
3. **依赖库链的证据等级**（用户评审结论，2026-10-13）：依赖库未入 Ghidra 的缺口**用基模先验知识补**——常见库（libc、liblog 这类）的函数语义（system/snprintf/strcpy 行为、`echo … >> file` 的 shell 语义）完全可信 LLM 先验，机械阶段给出的 ELF 级证据（导入表/PLT/字符串/重定位，全部自签 evidenceID）作为事实底座，两者合起来足以判定 lib 侧链；**只有自定义库**（无先验语义、无反汇编证据）才记 unresolved「无法判定」。因此原「Ghidra 加载依赖库」不再作为 lib 侧链 confirmed 的前置，降级为仅针对自定义库的可选增强（§6 R4 相应调整）。
4. **驳斥结论落点**：驳斥清单（§4）的结论 v1 写进 limitations（如「驳斥清单 R1-R4 均通过，依据 ev-…」），不加报告 schema 字段（契约不变原则）；若后续需要结构化统计（各驳斥项通过率）再扩 schema。

### 3.5 M2：一次有界 LLM 语义分类（采纳评审意见 ①）

> **实施状态（2026-10-14）**：本节暂缓落地。用户决定语义优化模块先不接入，M1（机械枚举）+ M3（机械去重）保持完整；`risk_chains.classify_with_llm` 已实现且只被单测覆盖，`cli.py` / `phase_m_worker.py` 都不构造 LLM 客户端，`risk-chains.json` 的 `stats.m2Used` 恒为 false。脱离 CLI 底座的 Anthropic Messages 客户端见 [docs/19](./19-Anthropic兼容客户端.md)。

TaintSage 的 P0「source/sink 识别」本就有 LLM 语义部分（外部函数参数级角色识别）；本方案把它从后期提示词**提前为阶段 M 的一个子步骤**，但保持有界：

- **范围**（一次调用、结构化 JSON 输出、无工具循环）：
  1. 外部函数调用点参数级角色识别——候选外部函数（recv/strcpy/snprintf/system…）在**当前调用点**是 source 还是 sink、哪个参数 `(f, idx)` 受控（TaintSage 式外部函数识别）；
  2. rodata 候选字符串语义分类——命令串 / 格式化串 / 令牌 / 日志 / 无关；
  3. 自定义库 vs 常见库判定——支撑 §3.4 决策点 ③ 的先验条款。
- **四条边界**（对「加入 LLM 增强」的约束，回答评审问题"怎么样"）：
  1. M1 机械枚举是**不变的地板**，LLM 只做分类、降权、补候选，永远不负责唯一枚举——漏报下限不受模型波动影响；
  2. **单次有界调用**（输入=候选清单摘要，输出=分类表），不得演变成第二个 agent 探索阶段；
  3. 失败/超预算 → 纯机械降级 + warning 日志（与 §3.3 降级一致）；
  4. 分类结果写入 risk-chains.json 作为阶段 J 的**先验引导**（排序、高亮、语义提示），不直接决定 verdict。
- 与 docs/13 P0 的关系：P0 的机械部分已在 M1，LLM 语义部分即本步；P0 不再需要独立的提示词阶段。

### 3.6 M3：机械去重（采纳评审意见 ②，LLM 判定之前）

阶段 J 的 token 与时长随链数线性增长（[Sifting the Noise](https://arxiv.org/abs/2601.22952) 亦指出 agent 框架间成本差距巨大），因此链进入 LLM 之前先做一次**纯机械去重**，规则取自 docs/13 P2 的 TaintSage RDC 去重：

1. **等价链合并**：同 source、同 sink、同 hops 前缀的多条链合并为一条，evidenceIDs 并集；
2. **保留更长链**：链 A 是链 B 的严格前缀（子链）时并入更长的超链；
3. **共享下游合并**：多条链在汇合点后共享同一段 sink 下游，合并为一条多 source 链。

正确性边界：只在**同 CWE sink 家族内**合并；每次合并保留被合并链的 evidenceIDs；risk-chains.json 的 `stats` 记录 `dedupBefore`/`dedupAfter`。规则纯机械、可单测；误合并的代价由阶段 J 的驳斥清单 R2 兜底（逐跳传播仍按全链核验）。

## 4. 阶段 J 设计（agent 逐链判定 + 驳斥式降 FP）

- **输入**：CWE 模板「起点」节改为「对给定候选链逐条判定」——注入 risk-chains.json 摘要（§3.3 预算），模型不再做 sink 枚举；模板继续保留判定规则、confirmation 政策与证据要求。
- **判定契约**：每条链给出 verdict（confirmed/rejected/unresolved）+ 理由 + 证据引用（允许就链上特定跳发起有界补充查询，预算沿用现有工具预算）；输出仍走现有 findings/coverage/report.json schema（`confirmationBasis` 沿用），**finalize 证据门禁、覆盖账本、PoC 全部不变**。
- **依赖库跳的先验判定条款**：链上跳落在依赖库内时，模型可用「机械 ELF 证据（evidenceID 可引用）+ 常见库函数语义先验」完成判定——报告中须把先验部分写进 limitations（如「liblog:system 的 shell 执行语义来自模型先验知识，机械证据为导入表/PLT/rodata 字符串」），不得伪造不存在的工具证据；**自定义库**（无法从导入/字符串/先验确定语义）判 unresolved 并写明原因。
- **驳斥式判定协议**（采纳评审意见 ③：借鉴 vh FOOLISH 的"愚者反问"交互，不照搬 22 问）：vh 的 FOOLISH 用 22 问四阶段（capability/feasibility/consequence/mitigation）迭代精化安全主张（见 [ProtectAI vulnhuntr](https://github.com/protectai/vulnhuntr)）；我们取的是**逐主张反问**的交互形态，压成 4 项驳斥清单，只对 confirmed 候选执行：
  - **R1 source 可控性**：攻击者真的能控制该 source 字节吗？
  - **R2 逐跳传播**：每一跳都能把污点传到下一跳吗（无长度/类型/截断屏障）？
  - **R3 清洗与约束**：路径上有没有显式清洗、格式约束、白名单？
  - **R4 构造与影响**：攻击者能否构造出恶意 payload 并被 sink 实际执行？
  - 裁决规则：任一驳斥项给出机械证据反证 → **rejected**（写明反证）；任一项无法核验 → **unresolved**；四项全过 → confirmed。每项最多一次有界补充查询。
  - 外部 practice 依据：
    - [Refute-or-Promote（arXiv:2604.19049）](https://arxiv.org/abs/2604.19049)：对抗式阶段门禁——候选在每个晋升门禁被对抗代理尝试证伪，171 候选 kill 约 79%（回溯）/83%（前瞻）；最深刻教训：10 个评审一致背书不存在的 Bleichenbacher oracle，仅实证测试杀掉 → **强制实证门禁**。映射到我们：不做动态执行，"实证门禁"= 机械事实（finalize 证据门禁保持），驳斥清单的通过与反证都必须落在证据上，不许口头放行。
    - [Sifting the Noise（arXiv:2601.22952，ISSTA 2026）](https://arxiv.org/abs/2601.22952)：agent 式 FP 过滤有效（OWASP Benchmark FP 92%→6.3%；post-cutoff 数据集 FP 识别 95.5%@95.5% 精度 vs 36.4% 纯提示词），但**强 backbone 依赖**、**激进过滤会压死真漏洞**（trade-off）、框架间成本差距巨大。→ 我们的响应：`--confirmation recall` 默认、每条 rejected 必须写具体反证、M3 去重与 16KiB 摘要控成本。
- **效率设计**：v1 = 单会话内置两遍式——先逐链判定，再对 confirmed 跑驳斥清单自驳一遍；不引入第二个模型/第二个会话。跨模型批评（Refute-or-Promote 的 CMC）列为 R4 后续可选。驳斥结论写入 limitations（§3.4 决策点 4），v1 不加报告 schema 字段。
- **与现有提示词改动的衔接**：上轮的两阶段 attack-surface.md 重写里「第一阶段枚举指引」移入机械阶段（代码），提示词只保留「第二阶段判定规则 + 驳斥清单」；6 个模板的去 vh 化保留。

## 5. 与既有方案/文档的关系

- **docs/13（TaintSage 接入）**：本方案把其 P2「RDC 物化」提前为前置机制，并把 P0「source/sink 识别」整体纳入阶段 M（机械部分=M1 枚举，LLM 语义部分=M2 分类，P2 去重=M3）；P1 Juliet 基准评测顺序不变，仍是量化 recall/precision 的闭环。
- **docs/14（攻击面侦查阶段）**：阶段 0 攻击面产物是 source 候选的上游输入；本方案 v1 独立实现不依赖它，合并为组级一次物化时再衔接（§3.4 决策点 1）。
- **docs/17（确认门禁保守性分析）**：闸门 ①（提示词自我降级）由阶段 J 的逐链判定契约缓解——模型拿到的是机制给的全量候选，不再因"自己没查到"而降级；闸门 ②③④ 语义不变。
- **上轮「两阶段提示词」**：方向修正——"广"从提示词下沉到机械机制，提示词只留"收"。相关文档（docs/17 §6.3、部署与使用手册 §5.5 两阶段段、PROGRESS 对应 bullet）在本方案落地时同步修订。

## 7. 风险与回滚

| 风险 | 缓解 |
|---|---|
| 链爆炸/摘要超预算 | §3.3 排序截断 + `truncated` 标注；提示词预算上线前用 fake 统计 |
| paths 后端耗时（逐 sink 查询 × N sink） | 预算沿用；机械阶段无 LLM 成本；慢时按 CWE sink 表优先序 |
| 模型不再枚举 → 机械阶段漏 sink 即漏报 | sink 家族表与模板 sink 表同源维护 + R2 回归断言模板与常量一致 |
| 常见库先验判定引入 FP（把语义猜错/张冠李戴） | 先验只允许用于常见库且必须在 limitations 写明依据；precision 模式与逐链反证兜底；自定义库一律 unresolved |
| M2 LLM 分类失败/方差 | 单次有界调用 + 失败降级纯机械；分类只做引导，verdict 由 J 决定 |
| M3 去重误合并（不同洞并成一条） | 只同 sink 家族内合并 + 保留 evidenceIDs + 单测规则；合并后 J 仍按全链做 R2 逐跳核验 |
| 驳斥协议过度过滤压死真漏洞（Sifting the Noise 教训） | recall 默认 + rejected 强制写具体反证 + R3 与基线对比链 A 不回退 |
| 驳斥协议抬高 J 成本 | 只对 confirmed 跑全清单 + 每项最多一次查询 + 结论写入 limitations 不扩 schema |
| 对现有 confirmed 行为回归 | R3 以 run-3939894a5123 为基线对比；r01/r02 契约不变 |
| 机械阶段异常 | 降级为现状行为 + warning 日志（§3.3） |
