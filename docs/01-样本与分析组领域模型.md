# 样本与分析组领域模型

状态：讨论稿 v0。

本文定义输入整理模块的边界。它把用户提供的文件整理为组件、关系和分析组，供后续静态分析使用。它不负责反编译、漏洞判断、Agent 推理或报告生成。

## 输入

模块接受：

- 单个 ELF
- 包含多个文件的目录
- 压缩包
- 固件镜像

固件解包由外部适配器完成。本模块只接收提取结果及其来源信息。

## 核心概念

样本是一次分析的完整对象，包含原始输入、提取内容、组件关系、分析组和来源信息。

输入容器是用户提供的文件、目录、压缩包或固件镜像。产物是从输入容器中发现或提取的文件、数据块和目录项。每个产物都要能追溯到输入、路径、偏移或提取过程。

二进制组件是可分析的 ELF、共享库或加载模块。上下文产物包括配置、脚本、字符串资源、符号文件和版本信息。上下文可以提供线索，但不能因为路径相邻就被当成二进制事实。

组件关系描述依赖、符号、加载、路径和固件来源。每条关系都要记录来源和可信度。工具确认的关系与模型推断分开保存。

分析组是一组需要共同理解的二进制组件及其上下文。系统自动生成分析组，不要求用户手动分组。没有可识别关系的组件形成单成员分析组。共享依赖可以被多个分析组引用，但保持同一个组件身份。

分析任务以分析组为默认目标。本模块提供任务目标，不执行分析。

## 处理过程

```text
输入容器
  → 发现或提取产物
  → 识别二进制组件
  → 建立组件关系
  → 自动生成分析组
  → 输出来源和状态
```

每一步都要能报告部分成功和部分失败。单个损坏或不支持的文件不能阻塞其他组件，但失败状态必须进入样本结果。

## 必须保持的行为

- 原始输入不被覆盖。
- 每个产物都能追溯到输入来源。
- 相同内容可以去重，不同路径仍要保留。
- 每个已识别组件至少属于一个分析组。
- 共享依赖可以属于多个分析组。
- 没有依赖关系的 ELF 仍然可以形成单成员分析组。
- 项目内没有对应文件的依赖形成待处理关系；常见库可以转为通用库知识引用，不能被静默忽略。
- 输入无效、格式不支持、工具失败和关系不确定要有不同状态。
- 非 ELF 文件可以作为上下文保存，但不能自动成为漏洞证据。

## 典型场景

单个 ELF 直接形成一个组件。没有其他关联时，它形成单成员分析组。

目录中有多个独立 ELF 时，它们分别成为组件并形成多个单成员分析组。若两个 ELF 共享同一个 `.so`，系统生成两个相关分析组，并让它们引用同一个库组件。

固件解包后，ELF、库、配置和脚本按照可确认的关系组织到不同分析组。路径、分区、偏移和启动信息作为上下文保留。

文件损坏或依赖无法继续处理时，其他组件继续处理。样本结果明确列出失败和待处理关系。

## 与其他模块的边界

输入和解包适配器提供产物及来源，不把某个工具的内部对象带入领域模型。

静态分析引擎接收分析组、组件身份、架构、路径和关系，返回函数、调用图和反编译等分析产物。

CWE 插件以分析组为输入，引用组件和上下文，不重复建立基础关系。

Agent 可以查询样本、组件和分析组，但不能直接改写来源关系。新的推断关系必须记录推断来源和状态。

## 暂不处理

- Ghidra 项目和反编译逻辑
- 污点传播、数值约束和漏洞判断
- Agent 提示词和会话管理
- 报告排版
- 用户手动修改分组
- 动态执行样本

## 待确认

- 固件自定义加载关系的表达方式
- 共享组件的分析缓存边界
- 分析组变化后的增量处理
- 后期交互工作区是否允许用户修改自动分组
