## 2. 证据引用完整性审计（防幻觉）

对两轮共 11 个 run 目录的全部 `report.json` 做交叉校验：报告文本与 findings 字段引用的每个 `ev-…` 是否都能在 `raw/{ghidra,paths}.jsonl` 中找到。

结果：**共引用 100 个 evidenceID，缺失 0**。门禁链条（evidence_proxy 记账 → finalize 核验 → coverage ledger）在真实运行中有效。

自动化脚本：`scripts/check_evidence_integrity.py <产物根目录>`，退出码非 0 表示发现无法追溯的引用。审计只统计结构性引用位置（findings/functionModels/attackSurfaces/pathQueries 与 propagationMap 条目的 `evidenceIDs` 数组），诊断文本中的 ID 字样不计入。

并发第 3 轮审计发现并修复一个门禁缺口：run-80e26d98d2d7（CWE-416）的函数模型/攻击面/propagationMap 条目引用了代理从未签发的 `ev-7cc5a1964e66c4c1303a`（模型幻觉 ID）。此前门禁只对 finding 的坏引用生效（移入 unresolved），模型/攻击面上的坏引用会留在报告里。修复（src/agent/artifacts.py finalize）：函数模型/攻击面的坏引用剔除、保留对象本身；propagationMap 中含坏引用的条目整体剔除；均记 unresolved（`证据引用无法核验`/`传播关系证据引用无法核验`）。回归测试 `ArtifactTests.test_model_and_surface_hallucinated_evidence_is_stripped`。修复后对存档 run 重新 finalize 复核，6/6 通过。

## 4. 漏报（FN）风险与改进计划

1. **GhidraMCP 会话时连时不连（当前最大 FN 源）**。两轮 12 个会话中仅 7 个连上；未连上时 agent 降级为 objdump+paths，候选链只能停在 candidate（fixture 证明 ghidra 连上时同一条链可以走到 confirmed）。改进：① 已加 `工具证据 ghidra=0` 日志行作即时告警；② 待做——opencode MCP 启动重试/超时调优，或运行后自动检测 `ghidra=0` 并建议重跑该 CWE；③ 根因待查（疑似 ghidra 项目锁残留或 opencode 服务器启动超时）。
2. **跨二进制路径无工具覆盖**（server→libauth.so/liblog.so），结构性 FN。对策在 docs/13 P2（RDC 物化）与 docs/15 固件方案中，本轮不展开。
3. **paths 后端只证明函数内定义链**，source 可控性证明不足时结论保守为 candidate。这属于"证据不足不确认"的正确行为，而非缺陷；提升确认率依赖上一条。

## 5. 结论

当前系统在 demo 上：**误报 0（所有 findings 均可追溯、可复核），漏报风险集中在 ghidra 会话抖动与跨二进制覆盖**，两者均有明确日志告警与路线图。优先级：先稳定 ghidra MCP 连接（直接决定确认率），再做跨二进制路径覆盖。
