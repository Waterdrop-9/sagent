# 静态污点传播工具调研

状态：方案调研，2026-10-11。

本文比较可用于 ELF 二进制、Ghidra 工作流和 CWE Agent 的静态污点/数据流工具。目标不是立即选出“全能工具”，而是确定一个可以快速落地、证据可回溯、后续可替换的 `query_sink_paths` 后端。

## 结论先行

当前最合适的组合是：

```text
elf.py 读取 ELF 并形成 analysis group
  → GhidraMCP 负责反编译、函数、调用图、字符串和交叉引用事实
  → 独立的路径查询后端负责参数级、sink 驱动的数据流搜索
  → Agent 负责按 CWE 选择查询、解释语义、整合证据和筛除误报
```

第一阶段不建议让 Agent 自己在反编译文本中“模拟完整污点传播”。本文只做能力和集成评估，尚未在本仓库的 ELF 样本上对这些工具进行基准测试；工具排名和选型结论需要经过同一正/反例集的实际试跑。LLM 可以帮助识别包装函数、source/sink、sanitizer 和查询优先级，但寄存器、栈变量、内存别名、调用点参数映射和路径去重应由确定性工具完成。否则结果难以复现，也很难证明一条路径确实存在。

建议优先验证两条现成路线：Mango（已经以 sink 为起点，开箱提供命令注入分析）和 CTADL（直接利用 Ghidra P-code，支持自定义 source/sink/外部函数模型）。若它们不能满足我们的调用点证据和按需查询契约，再实现一个小型 angr RDA 适配器。下面的结论来自文档和源码能力审查，尚未在本仓库样本上运行这些污点工具，不视为完成选型。

候选工具的定位如下：

| 工具 | 输入 | 跨函数/参数级能力 | 证据可验证性 | 部署成本 | 适合本项目的角色 |
| --- | --- | --- | --- | --- | --- |
| Mango | 二进制/固件 | sink 驱动、跨函数 taint-style 分析；默认命令注入 | 中高：JSON closure、trace、sink、inputs 和文件哈希 | 中：独立 Python 环境或 Docker；需验证依赖版本 | CWE-78 第一轮现成后端试验 |
| CTADL | Ghidra P-code 等 | 跨过程、可定义 source/sink 和外部传播模型 | 中高：SARIF 路径；仍需验证二进制地址映射质量 | 中高：旧版 Python + patched Soufflé，新版 Rust 仍在变更 | Ghidra 路线首选评估对象 |
| angr | 多架构二进制 | RDA/FunctionHandler、CFG、DDG、VFG、BackwardSlice；需配置语义模型 | 中高：定义、依赖图、CodeLocation；别名仍有限制 | 中：Python 依赖和分析耗时；需写适配器 | 现成后端不足时的可控参数查询基座 |
| EmTaint | 嵌入式固件二进制 | 面向 taint-style 漏洞，SSE 按需别名分析、间接调用解析、sanitizer 规则 | 中高：能输出告警和路径，但分析假设较多，需检查版本和规则 | 高：依赖特定 angr 环境，官方实验使用 Docker | 研究基线或后续离线批量分析，不作为第一版运行时依赖 |
| BinCAT | 二进制，支持独立 analyzer 与 IDA 集成 | 有值分析、污点分析、前向/后向分析；参数和状态需配置 | 中：寄存器/内存 taint 状态可回看；结果数据模型与本项目不同 | 高：OCaml 构建；官方 macOS 流程不再测试，建议 Linux/容器；IDA 仅插件路径 | 不纳入当前主线；可作对比实验 |
| PhASAR | LLVM IR | IFDS/IDE 等跨过程数据流和 alias-aware taint | 高：IR 指令和分析结果稳定 | 高：需要 LLVM IR/构建链；不能直接处理任意 stripped ELF | 有源码或可重编译样本时的旁路验证 |
| CodeQL | 支持语言的源代码/编译过程 | 成熟的 source/sink、barrier、path query 模型 | 高：数据库、查询和路径结果可审计 | 高：需要正常构建/抽取；不面向任意 stripped ELF | 源码可得时的 CWE 交叉验证，不是二进制后端 |
| Ghidra/GhidraMCP | 二进制及其 Ghidra Program | 反编译、P-code、函数、调用、字符串、交叉引用；核心不提供完整通用污点分析 | 高：地址、P-code、反编译文本和引用可回溯 | 已在项目中部署；MCP 只需配置 Ghidra | 事实和语义导航层，作为所有查询的证据来源 |

## 1. angr

angr 是面向多架构二进制的 Python 分析框架，覆盖加载、IR、CFG、静态分析和符号执行。[官方快速入门](https://api.angr.io/en/latest/quickstart.html)说明它支持依赖分析和程序切片；[官方分析列表](https://docs.angr.io/en/v9.2.74/core-concepts/analyses.html)列出 `CFGFast`、`CFGEmulated`、`DDG`、`VFG` 和 `BackwardSlice` 等组件。

对我们的 workflow，angr 的价值在于可以围绕一个 sink 参数做可编程查询：

```text
sink callsite + argument
  → CFG / IR 定位
  → ReachingDefinitionsAnalysis / DepGraph
  → 从 sink 参数定义反向遍历
  → 跨函数边和调用点参数映射
  → 返回带地址和 IR 节点的路径
```

更贴近参数级查询的是 [ReachingDefinitionsAnalysis（RDA）](https://docs.angr.io/en/v9.2.223/api/angr.analyses.reaching_definitions.html)：支持 VEX/AIL、观察点、定义和使用链。其 [FunctionHandler](https://docs.angr.io/en/latest/api/angr.analyses.reaching_definitions.function_handler.html)提供跨函数深度、参数定义、返回定义和调用点 `CodeLocation`，能够挂接已知库函数的传播模型。建议围绕 RDA 构建适配器，而不是直接把普通 DDG 当作污点结论。RDA 官方文档本身也提示 aliasing 限制，因此仍需显式记录未知内存依赖。

需要注意精度边界。[angr API 文档](https://docs.angr.io/en/latest/api/angr.analyses.html)明确指出普通 `DDG` 只反映构建 CFG 时观察到的简单数据依赖，不保证 sound 或 accurate；更精确的 VSA-based DDG 需要先进行更重的值集分析。这个限制非常适合写入工具输出：每条边应记录分析模式、上下文敏感度和未覆盖的别名/间接调用情况，不能把结果标成“完整污点证明”。

angr 的优点：

- 直接接受 ELF，适合 stripped binary 和多架构样本；
- Python API 容易包装成 MCP tool；
- 可按 sink、参数、函数范围和深度做按需查询；
- 结果可以保存 CFG/IR 地址、调用点和切片节点，便于证据回溯；
- 后续可以接符号执行或约束求解，帮助重判可达性。

angr 的限制：

- 不是开箱即用的 CWE 污点扫描器，source/sink、sanitizer、参数语义需要项目自己定义；
- 间接调用、函数指针、复杂别名、堆内存和异常控制流会影响结果；
- 分析成本可能随 CFG、上下文敏感度和路径数量快速增长；
- Agent 仍需要解释反编译语义，不能只读取图结构。

因此建议把 angr 包装成受预算约束的 `query_sink_paths` 后端，而不是让 Agent 直接调用任意 angr API。接口至少应接收组件、sink 函数/地址、参数编号、source 候选、深度和节点预算，返回结构化路径和“不确定/未覆盖”原因。

## 2. EmTaint

[EmTaint 官方仓库](https://github.com/kuc001/EmTaint)定位为嵌入式固件的静态 taint-style 漏洞分析工具。其 README 描述了基于 structured symbolic expression（SSE）的按需别名分析，用来处理隐式数据流和控制流；同时实现间接调用解析、污点分析和 sanitization rule checking。对应论文是 [Finding Taint-Style Vulnerabilities in Linux-Based Embedded Firmware](https://arxiv.org/abs/2109.12209)。

EmTaint 与我们的 TaintSage-inspired workflow 很接近：先围绕潜在 sink/入口筛选路径，再按需进行更精细的别名和传播分析。它值得复用的主要是方法和实验基线：

- 按需解析别名，避免一开始对全程序做昂贵传播；
- 把间接调用解析放在 taint path 之前；
- 将 sanitizer 规则作为误报筛除的一部分；
- 输出漏洞告警和传播路径，便于和 Agent 的证据整合对接。

但不建议在 MVP 直接依赖 EmTaint：官方仓库要求特定的 angr 环境，并建议使用发布的 Docker 镜像；脚本、数据目录和实验入口偏向论文复现，而不是稳定的服务 API。部署和升级将绑定论文实验的专用环境，实际可移植性需要试跑确认。

建议：把 EmTaint 作为后续评测基线或离线批处理后端；论文仓库和镜像的许可证、依赖版本需在真正集成前单独核对。先复用其“按需别名 + 间接调用 + sanitizer”思想，在项目内定义更小、可验证的路径查询接口。

## 3. BinCAT

[BinCAT 官方仓库](https://github.com/airbus-seclab/bincat)是静态 Binary Code Analysis Toolkit，提供值分析、污点分析、类型重建和传播、前向/后向分析，以及 use-after-free 和 double-free 检测。它支持通过 IDA 插件或 Python 自动化，并列出 x86-32、x86-64、ARMv7、ARMv8 和 PowerPC 等架构。

BinCAT 的优点是污点和值分析已经做成了逆向工具中的交互式能力，分析结果对人工审计比较直观。官方手册同时支持独立 analyzer 和 IDA 集成，但安装手册的完整依赖仍然很重，macOS 流程也已不再测试，推荐 Linux 或容器。我们的主线使用 Ghidra/GhidraMCP；直接接入 BinCAT 会引入第二套 IR、配置和证据数据模型。

因此 BinCAT 官方仓库标注为 AGPLv3；不作为当前主线后端。它可以在后续对同一个样本进行交叉验证，尤其适合验证值传播、寄存器/内存污点和人工可疑路径，但不应成为本项目的基础依赖。

## 4. PhASAR

[PhASAR 官方网站](https://phasar.org/)和[官方仓库](https://github.com/secure-software-engineering/phasar)将其定义为基于 LLVM IR 的 C++ 静态分析框架，提供通用数据流求解器、调用图和 points-to 分析。[官方教程](https://phasar.org/tutorial/)要求先把源代码编译为 LLVM IR；[官方运行分析说明](https://github.com/secure-software-engineering/phasar/wiki/Getting-Started%3A-Running-an-Analysis)列出 `ifds-taint` 等 alias-aware taint analysis。

PhASAR 的优势在于跨过程数据流框架成熟，IFDS/IDE 适合可复现的 source/sink、summary 和路径查询，且结果容易映射回 LLVM 指令。对于有源码、能控制编译选项的 C/C++ 项目，它可能比从机器码恢复参数关系更稳定。

但我们的输入是 ELF 分析组，可能没有源代码、调试信息或可重编译环境。把任意 stripped ELF 重新可靠地还原为 LLVM IR 不在 PhASAR 的能力范围内，部署还需要匹配 LLVM 版本和编译链。因此 PhASAR 适合作为“源码可得样本”的旁路验证器，或未来在固件厂商提供构建产物时使用；不适合作为现阶段主路径后端。其项目采用开源许可证，但实际接入前仍应核对所固定版本的许可证和 LLVM 兼容性。

## 5. CodeQL

[CodeQL 官方文档](https://codeql.github.com/docs/)支持用 QL 查询代码数据库，并提供 source/sink、barrier、path query 等安全分析模型。可是其数据库创建依赖支持语言的源代码或正常编译过程：[官方关于 CodeQL](https://codeql.github.com/docs/codeql-overview/about-codeql/)说明编译语言的 extractor 通过监控编译器调用来采集语法和语义信息；[支持语言列表](https://codeql.github.com/docs/codeql-overview/supported-languages-and-frameworks/)列出 C/C++ 等受支持语言和编译器。

CodeQL 对 CWE 工作流很有吸引力：查询、库、测试和 path explanation 都能版本化，误报屏蔽可以表达为 barrier/guard，结果也适合审计。但它面向源码/编译数据库，不是针对任意现成 ELF 的二进制数据流工具。对 stripped binary，缺少 CodeQL extractor 所需的编译期语义和类型信息，无法直接替代 Ghidra/angr。

建议仅在源码可获得时，把 CodeQL 作为同一 CWE 的交叉验证通道；二进制主线不引入 CodeQL 运行时。

## 6. Mango 与 CTADL：更值得先试的现成后端

### Mango

[Mango 作者仓库](https://github.com/sefcom/operation-mango-public)（BSD-3-Clause）和 [USENIX Security 2024 论文](https://www.usenix.org/system/files/usenixsecurity24-gibbs.pdf)采用从 sink 回溯的 taint-style 分析，用已知函数模型跳过不必完整分析的函数，避免全程序 top-down 路径爆炸。默认 `mango` 命令执行命令注入分析，输出 JSON 的 closure、函数 trace、sink、likely/possible inputs、文件哈希和耗时；`TOP` 表示未知/不可解析值。它还有 env/nvram 多二进制关联能力。

这使 Mango 比“直接从 angr 原语重新写一个漏洞扫描器”更适合先验证 CWE-78 demo。但它的 assumed execution 和 unknown values 仍是近似，rank 不是可利用性的证明。集成时应保留完整 trace，不使用会删除路径细节的 concise 输出；依赖版本、任意 sink 参数查询和跨库行为需实际试跑确认。它适合作为候选链生成器，Agent 仍要用 Ghidra 复核 source 可控性和 sanitizer。

### CTADL

[Sandia 的 CTADL](https://github.com/sandialabs/ctadl)明确支持 Ghidra P-code 的跨过程污点分析和 SARIF 路径输出。它把 import、index 和 query 分开，并可定义外部函数传播模型，适合一份二进制事实支持多个 CWE 查询。旧版依赖 Python 和特定 patched Soufflé；作者已经将新开发迁到 [CTADL Rust 版本](https://github.com/sandialabs/ctadl-rs)（Apache-2.0）。新版可从二进制或 Ghidra project 导入 P-code，模型文件支持 source、sink 和 external propagation。

这条路线与现有 Ghidra 事实层贴合，也比让 Agent 手工做所有参数传播更可复现。不过新版 README 明示命令、flag 和文件格式仍可能改变；不能只因它有 SARIF 就假定所有路径边有完整机器码地址。先在同一小型样本验证正例、常量参数反例和过滤反例，再决定是否固定版本接入。

## 7. Ghidra 与 GhidraMCP

[Ghidra 官方仓库](https://github.com/NationalSecurityAgency/ghidra)提供反汇编、反编译、程序分析、脚本和 P-code 基础能力。项目当前使用的 [GhidraMCP](https://github.com/LaurieWired/GhidraMCP)把 Ghidra 的函数、导入/导出、字符串、反编译、调用关系和交叉引用能力通过 MCP 暴露给 Agent。

Ghidra 最适合承担“事实和导航层”：

- 确认函数入口、地址和程序架构；
- 获取反编译文本；必要时通过 Ghidra API 单独提取 P-code 位置（当前 MCP 工具集合是否暴露 P-code 需要逐项核对）；
- 枚举导入、导出、字符串和调用边；
- 检查某个调用点的 callers/callees/xrefs；
- 为 Agent 提供解释 source、sink、wrapper 和 sanitizer 所需的上下文。

Ghidra 核心并不是一个已经定义好 source/sink 规则的通用跨函数污点引擎。因此应避免把“调用 GhidraMCP 查到反编译代码”误称为静态污点分析。我们需要单独的路径查询工具：它可以采用 CTADL 分析 Ghidra P-code，或由 angr 独立加载同一个 ELF。angr 的 VEX/AIL 和 Ghidra P-code 是不同 IR，不能直接互换；以文件哈希、image base 和地址建立证据关联。Ghidra 提供 P-code emulator API，可用于特定轨迹的实验；轨迹仿真与静态的全路径跨函数查询是不同能力，不以此替代当前查询后端。

## 8. Agent 自行传播分析的评估

让 Agent 自己阅读每个函数并逐个判断“参数 1 是否流到返回值/参数 2”有一个明显优点：对未知包装函数、字符串拼接、协议字段和 sanitizer 语义很灵活，且无需先为每个架构写完整规则。

但它不能独立承担核心传播：

- 它会把调用关系误当成数据依赖；
- 对寄存器、栈槽、内存别名和函数指针缺少稳定的全局状态；
- 相同问题可能重复查询，输出难以去重；
- 上下文窗口和工具调用预算会随 source/sink 数量增长；
- “没有看到传播”不等于证明不存在传播；
- 结果若没有地址、IR/P-code 节点和调用点映射，后续无法审计。

更合适的分工是：

```text
确定性后端：函数/调用图、参数映射、切片、别名近似、路径搜索、去重
Agent：候选排序、未知函数语义、source/sink 分类、sanitizer 判断、补充查询、证据重判
```

如果静态工具只返回粗粒度候选，Agent 可以请求更细的 `inspect_callsite` 或 `query_sink_paths`；如果工具发现别名、间接调用或架构语义未覆盖，必须把限制作为结构化结果返回，让 Agent 输出 `inconclusive`，而不是自行补全事实。

## 9. 针对当前项目的落地建议

### 第一阶段：Ghidra 事实 + 小型参数路径查询

保留 GhidraMCP 作为唯一反编译和二进制导航入口，增加一个独立的路径查询后端，先支持：

- sink 函数/调用点和参数编号；
- 参数到参数、参数到返回值、返回值到调用点参数；
- 直接调用和有限深度间接调用；
- 基本寄存器/栈变量和简单内存读写；
- 每条边的地址、函数、调用点、IR/P-code 位置和分析限制；
- 最大深度、节点数和时间预算。

先用同一批最小样本试跑 Mango 和 CTADL，评估：

- 外部输入经过两层 wrapper 到 `system` 的正例；
- sink 参数为常量、与输入无关的反例；
- 有白名单/转义的重判例；
- 指针输出参数、间接调用、跨分析组组件的未覆盖例。

比较 sink 参数、每条传播边、机器码地址、原始工具结果和耗时。若现成工具能满足接口，优先写适配器；否则基于 angr `CFGFast + calling convention recovery + RDA/FunctionHandler` 做范围受限的查询。工具不完整时保留 `inconclusive`，Agent 可进一步读代码补充语义证据，但不能覆盖静态工具的不确定性。这个阶段不引入 TaintSage cache 或 RAG。

### 第二阶段：按需增强

当第一阶段暴露出真实样本中的误报来源后，再针对需要的部分引入：

- VSA 或更精确的别名分析；
- 间接调用解析；
- sanitizer 和 CWE-specific 规则；
- 约束/符号执行辅助可达性复核；
- EmTaint 作为固件样本的对比基线。

### 第三阶段：多后端和交叉验证

将 `query_sink_paths` 定义成后端无关接口。未来可挂接：

```text
Ghidra facts + 一个或多个路径分析后端
```

候选后端包括 Mango、CTADL、angr、EmTaint，以及在源码可得时的 PhASAR/CodeQL。

Agent 不应知道具体后端实现，只读取统一的结构化事实和证据。这样当某类样本拥有源码、LLVM IR 或 EmTaint 适用的固件环境时，可以用第二个后端交叉验证，而不改变 CWE prompt 和误报复核流程。

## 10. 选择标准

后续评估任何新工具时，至少记录以下信息：

- 是否直接接受 ELF，是否要求源码、IR、IDA 或特定反编译器；
- 是否能表达 sink 参数级查询，而不是只有函数级告警；
- 是否支持跨过程、间接调用和别名近似；
- 返回结果能否定位到地址、调用点、IR/P-code 或原始指令；
- 能否报告未覆盖路径、超时和分析不确定性；
- source/sink/sanitizer 规则是否可版本化；
- 是否能在无样本执行的情况下运行；
- 安装、许可证、架构支持和批量分析成本；
- 能否被 MCP tool 包装，并被 Agent 按预算调用。

这组标准保证“工具能力”最终服务于证据驱动的 CWE workflow，而不是为了堆叠更多逆向工具。
